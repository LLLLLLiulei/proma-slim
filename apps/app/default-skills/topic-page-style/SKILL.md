# 专题页面布局与视觉设计指南

## 如何使用这份指南（渐进式加载，请先读完这一段）

这份技能分三层，不要一次性通读所有文件：

1. **本文件（SKILL.md）**——决策逻辑与设计判断力，每次触发都应完整阅读，这是"怎么想"。
2. **`references/`**——按需查阅的细节文档，只在决策已经做出、需要具体线框图/CSS类名/校验条目时才去读对应文件，不必通读。
3. **`assets/`**——可以直接复制拼接进产出物的现成代码（CSS、HTML骨架、JS）。**这些文件应该被直接读取并拼接，而不是凭记忆重新敲写**——重新誊写长代码是产生遗漏、语法错误的主要来源。

| 文件 | 内容 | 何时查阅 |
|---|---|---|
| `references/layouts.md` | 13 种布局、KV Banner、特殊专题模块的线框图、内容约束、易错点、对应的 CSS 类名 | 决策表或类型配方选定结构后，只看对应的一节 |
| `references/page-type-recipes.md` | 截图风格类型配方：政务、会议、门户资讯、文旅、公益纪实、榜单等 | 选定页面类型后读取对应一节 |
| `references/image-assets.md` | 宿主图片生成 MCP 自探测、Banner/KV prompt、搜索/导入回退、资产接入规范 | 任何首屏强视觉页面在写 HTML 前必须查阅 |
| `references/color-system.md` | 配色推导算法细节、5 个方向参考、防重复规则 | 需要确定具体配色数值时 |
| `references/qa-checklist.md` | 合并后的防坑清单与收尾检查清单 | 生成过程中的自检环节 |
| `references/examples.md` | 口语化需求到页面配方、Banner prompt、HTML 片段的轻量示例 | 需要校准执行方式或避免只复制骨架时 |
| `assets/base.css` | 完整可用的 CSS（token + 全部布局样式） | 落地代码阶段，直接复制后按主题改 `:root` 变量 |
| `assets/base.html` | HTML 骨架（Header-Tab-Content-Footer） | 搭建页面结构时作为起点 |
| `assets/tab-nav.js` | Tab 高亮/平滑滚动 + 轮播逻辑 | 页面含 Tab 导航或轮播时 |
| `scripts/validate_page.py` | 自动校验脚本（锚点完整性、禁用元素、布局重复等） | 有文件系统和 Python 时，生成完成后必须运行一次 |

## Page-builder 角色

在 `page-builder` 中，此 skill 是**执行型视觉 worker**：

- 在 `page-builder-guided-generation` 确认简报后、进入生成阶段时，用此 skill 指导视觉实现。
- 不负责首轮需求收集、用户确认、路由判断、CMS 绑定选择或二阶段细节 polish。普通用户对话仍由 `page-builder-guided-generation` 控制；但当上游把口语化需求摘要传进来（如“做个蓝白会议专题”“参考老式政务专题截图”“给公益活动做专题页”），本 skill 必须能直接把它归类为页面类型、布局序列、Banner 语义和视觉约束。
- 生成的页面必须遵循 page-builder 的 **HTML-first** 约束：纯 HTML/CSS/JS，不引入 React/Vue/框架。这类专题页本质是静态展示内容，不需要组件框架的运行时开销，vanilla 实现也更轻量、兼容性更好。
- 默认进入实现，不做长篇设计说明。规划可以在内部完成；除非用户要求解释，否则不要把长规划表输出到用户界面。
- **事实与内容安全**：保留用户明确提供并要求展示的真实事实；不要自行编造具体人名、机构名、电话号码、邮箱、日期、地址、证书编号或精确数据。会议天数、具体日期、议程时间、场次数、报名二维码、备案信息、主办/承办单位、联系方式都属于硬事实；用户未提供时用“拟设议题方向”“议程框架待发布”“报名信息待公布”等弱占位，不要做成确定数字或正式安排。嘉宾/讲师/发言人等缺少真实素材时用职务或机构泛称（如「行业协会代表」「高校研究团队负责人」）或明确占位符。核心原则：**不要让读者误以为模型编造的硬事实是真实存在的**。

### 图片策略

1. **优先使用用户提供、简报传入或宿主明确暴露的项目素材**。传统 CMS 专题页高度依赖真实会议、城市、活动、图集素材；不要用随机外链图片替代，也不要自行做 CMS/media binding 或猜测素材路径。
2. **按能力分层获取视觉资产，且必须自行探测工具**。不要把“没有 AI 生图工具”当作没有视觉资产能力；也不要把“没有已知工具名”当作没有生图能力。写 HTML 前先查看当前可用工具列表：若存在名称或说明包含 `generate_image`、`image_generation`、`text_to_image`、`create_image`、`image_generate` 等语义的宿主/MCP 工具，优先按其 schema 生成 Banner/KV；若无生图工具但有 `mcp__image_search__search_images` / `mcp__image_search__download_images`，则搜索并导入横向图；两者都不可用或失败时才回退 CSS/SVG。完整步骤见 `references/image-assets.md`。
3. **首屏强视觉页面必须先尝试获得 Banner/KV 资产**。会议、活动、培训、政务宣传、文旅专题、公益纪实、榜单/评选等页面，如果用户未提供 Banner/KV 素材，且探测到图片生成 MCP，必须先尝试生成 1 张首屏 Banner/KV 图；如果只有图片搜索/下载工具，则先搜索并导入 1 张横向图。只有生成、搜索和项目素材都不可用、不可用结果不合适、工具调用失败，或用户明确不要图片时，才降级为 CSS 几何/渐变占位。不要在最终 HTML 注释或用户回复中输出“无图片生成工具”“已安全回退”等内部判断。
4. **生成或搜索前先做图片语义判断**。页面任务词决定主场景；内容对象词决定辅助主体；领域词只作为背景、纹理、展板、图标、屏幕内容、线稿或抽象装饰；调性词决定色彩、光线、构图和装饰密度。当领域词与页面任务词冲突时，以页面任务词为准，不要仅因为领域词更容易出图，就把会议、培训、活动、政策或成果展示页面做成无关生产现场、设备特写、施工现场或负面风险画面。prompt 顺序：页面任务主体 → 内容对象 → 领域辅助元素 → 风格 → 禁用偏离场景。AI 生成风格段优先使用：`natural lighting, documentary style, subtle color grading, realistic texture, restrained composition, avoid generic stock photo aesthetics`。尺寸表、搜索词组织、返回路径接入和失败回退均按 `references/image-assets.md` 执行。
5. **按图片将要使用的区块决定生成尺寸**。宿主 MCP/图片工具支持尺寸参数（如 `width`、`height`、`aspectRatio`、`size`）时必须传入，不支持时在 prompt 中明确目标尺寸和比例。常用建议：首屏 KV/Banner 完整海报用 1920x420 或 1920x480，背景式 Hero 用 1600x900；焦点区/J 布局用 960x600 或 960x540；图库/E 布局主图用 960x540，小图用 640x640 或 640x480；B/F 卡片配图用 800x600 或 640x426。
6. **生成图片禁止绘制任何文字**。调用图片生成工具时，不要让图片里出现页面标题、口号、会议名、年份、日期、单位名称、logo、印章、标牌、二维码、汉字、英文字母、数字或任何排版文字；页面标题、口号、日期、单位名称必须由 HTML/CSS 渲染。若生成结果含文字、乱码或疑似字母数字（右下角“AI生成”等平台生成提示角标除外），必须换更强的 `no text, no letters, no numbers` prompt 重试；仍无法避免时改用图片搜索或 CSS/SVG 回退，不要把带字图片当成 KV。
7. **Header 图片结构必须正确**：生成成功后必须把图片写入 `assets/` 目录；搜索或导入成功同理，并在 HTML 中实际引用；不要生成了图片却继续使用纯 CSS Hero。用户提供的完整设计 KV/海报图可用 `.kv-banner` 或 `.hero--poster-image` 保持整图不裁切；AI 生成的 Banner/KV 默认是无文字视觉底图，使用背景式 Hero：`<img class="hero__bg" ...>` 作为 `.hero` 的直接子元素，后接 `.hero__overlay` 和 `.hero__content`，标题由 HTML 叠加。不要把背景图放进 `.hero__content`。
8. **AI 生成图片通常不做水印检查**。不要主动检查、报告或因为“AI生成”类平台提示角标阻断使用；只检查图片内容是否适合当前页面：主题贴合、画面积极中性、无乱码文字、无图片内标题/字母/数字、无可辨识人脸、无争议符号或明显不适内容。外部来源图片、用户/CMS 素材或疑似素材站图片才需要检查第三方水印、素材站 logo、版权署名、二维码或平台角标。
9. **CSS/SVG 回退要少而明确**：使用 `.hero-geo`、`.placeholder-visual` 或主题化 CSS 占位时，不要阻塞后续 section；但如果 Header 已经是 CSS/SVG 主视觉，正文中最多再使用 1 个同风格大视觉块，避免整页都是同色渐变和几何占位。无真实图片时不要堆大面积“伪图集”；可保留 `.gallery--asymmetric-compact`、普通 2x2 预留图、焦点占位、新闻列表或“图片持续更新”提示。
10. **禁止** `picsum.photos` 等随机图片占位服务。
11. **嘉宾/专家头像**：没有用户提供真实头像时，优先省略头像或使用 CSS 几何占位；不要生成假人脸照片。

## 一、设计哲学（做任何选择前先想这五条）

> **关于"参考页面"**：本文多处提到"参考页面"——指的是该 skill 设计时所依据的真实中文专题页样本集（政务、机构、会议、文旅等领域的传统 CMS 页面）。样本规律已沉淀到本 skill 的 `references/` 与 `assets/` 中；除非用户提供参考截图/链接，否则不要另找外部参考页，也不要凭记忆扩散到无关网站风格。

**口语化需求入口**：上游简报可能保留用户原话。遇到“做个专题页”“像老式门户专题”“仿会议截图”“给某活动做 Banner 和专题页”这类表达时，不要停在字面词；先提取主题对象、页面任务、硬事实、素材线索、期望风格和禁用项，再映射到 `references/page-type-recipes.md` 的页面类型。用户提供参考截图/链接时，先做视觉盘点：Header 类型、导航样式、内容壳宽度、标题变体、模块顺序、图文比例、色彩气质、图片密度、圆角/阴影和页脚形态；只复用布局和风格规律，不像素级复刻。

这份指南给了大量表格和数值，但表格解决不了"为什么这么选"。遇到表格没覆盖到的情况，回到这五条判断：

1. **内容决定布局，不是布局决定内容。** 决策表（第三节）是起点，不是唯一答案——如果一段内容明显不适合表里任何一种布局的字数/结构约束，优先调整实现细节去贴合内容，而不是削足适履改内容。
2. **每一个可选项都要被"选出来"，而不是被"漏掉后自动落到示例值"。** 标题变体、Header 形式、圆角大小、配色色相，这些维度都存在"看起来最省事的默认值"（比如左色条标题、渐变 Header、`#1A5FBF` 蓝）。如果每次都选它，页面就会千篇一律。第四节给出了强制显式选择的方法。
3. **配色和结构从主题推导，参考方向不是可以原样复制的答案。** `references/color-system.md` 里的几个方向是给你算法怎么用的例子，照抄它们的 hex 值和照抄一个模板没有本质区别。
4. **"看起来不像 AI 生成的模板"是硬约束，不是锦上添花。** 第三节的反 AI 感对照表要当作否决项来用：出现表格左列的特征，就是要修改的信号。
5. **先想清楚骨架再写代码，返工成本远高于多花时间规划。** 第六节的分阶段生成流程就是为了避免"写到一半发现结构冲突，从头重来"。

**进入决策前的自查**（读完原则后，确认以下三条再进入第三节决策表）：① 本次内容是否完全匹配某个布局的字数/结构约束？② 标题变体/Header/圆角/配色是否都将在第四节做显式选择？③ 配色是从算法推导的还是准备照抄参考方向的？如果第三条答"准备照抄"，回到原则 3。

## 二、页面架构（骨架）

所有页面共享同一套空间结构：**Header/Banner → 静态栏目导航（推荐）→ 内容区（传统 CMS 内容壳或 section 纵向堆叠）→ Footer**。完整可运行的骨架代码在 `assets/base.html`，直接以它为起点填充内容，不要从零重写。

| 区域 | 作用 | 高度/尺寸参考 | 是否必需 |
|---|---|---|---|
| Header | 主标题+副标题（可选英文副标题 `.hero__subtitle-en`），建立页面基调 | `min-height:30vh`（极简 `.hero--minimal` 为 `25vh`），最高到 `100vh` | 必需 |
| Tab 导航 | 栏目入口，信息密集型页面（会议/资讯/政务）推荐。传统 CMS 默认静态栏目条，sticky 仅作现代单页变体 | 40–52px | 推荐，叙事型页面（纪念/品牌主张）可省略 |
| 内容区 | 13 种布局任意组合，见第三节 | 由密度档位决定，见第五节 | 必需 |
| Footer | 版权/主办方/联系方式。多栏布局加 `.footer--multi` | `min-height:80px` | 必需 |

**内容宽度**：密度控制间距，内容壳控制宽度。传统 CMS 默认 `--shell-width:1040px`；门户窄壳 `960–1080px` 最贴近参考截图；宽内容 `1200px` 只给宽图集/榜单/数据页使用。紧凑控制的是间距，不等于无限制全宽。

**传统 CMS 默认内容壳**：多数参考页不是大面积交替 section，而是 `topic-shell` 内连续堆叠 `module-box`，通过白底、细边框、栏目横线和局部内边距分隔信息。除非用户明确要现代分段式落地页，否则优先使用：

```text
[Full-width poster/banner]
[Static tab nav]
<main class="topic-shell">
  <section class="module-box" data-layout="J">...</section>
  <section class="module-box" data-layout="M-twin">...</section>
  <section class="module-box" data-layout="D">...</section>
</main>
[Footer]
```

`section--alt` 交替底色是现代专题变体，不是传统 CMS 默认分隔方式。

**关于分栏的澄清**：参考页面**没有页面级贯穿侧栏**（不存在"全局左主栏+全局右侧栏"）。两栏内容（布局 B/J/M）都在 section 内部局部使用，与整宽 section 交替构成节奏，主体内容默认单栏通排。

## 三、内容 → 布局决策

### 决策流程

以下决策树按**内容类型的关键词**触发对应布局，但这不是唯一入口。**在走决策树之前，先问自己三个问题**——即使用户没有明确说出这些触发词：

1. **这段文字是否可以配图变成 B？** 任何有描述性内容的 section（介绍、概况、背景），如果长度足够，都可以从 A 升级为 B（双栏图文）。A 仅用于概述或极短的说明。
2. **这几个并列区是否可以分栏？** 两个内容量相近的 section，可以用 M（两栏并排或 twin-sections）消化横向空间，减少纯单列堆叠的单调感。
3. **是否存在头图 + 列表的组合？** 一个主视觉 + 几条新闻/要点 = J（焦点区），这是参考页面中最高频的模式之一，但很容易被漏掉拆成 A+I 两个单独 section。

```
用户说："我想展示 XXX"
          │
          ├─ 数据/数字/指标    ──→  布局 C: 数据展示行
          ├─ 图片+文字介绍     ──→  布局 B1/B2: 双栏图文
          ├─ 多张图片展示      ──→  布局 E: 图片画廊
          ├─ 多个并列条目      ──→  布局 F: 列表卡片(上图下文或无图)
          ├─ 时间线/历程       ──→  布局 D: 时间线
          ├─ 新闻/资讯条目     ──→  布局 I: 新闻列表行
          ├─ 头图+重点新闻     ──→  布局 J: 焦点区(左大图+右列表)
          ├─ Header轮播图      ──→  布局 K: Hero轮播
          ├─ 横向滑动图片      ──→  布局 L: 内容区滑动
          ├─ 需要双栏并排内容   ──→  布局 M: 两栏并排（section 内局部使用）
          ├─ 需要栏目切换导航   ──→  布局 H: Tab 导航（信息密集型页面推荐）
          ├─ 大段文字/说明     ──→  布局 A: 纯文卡片
          └─ 联系/报名/表单    ──→  布局 G: CTA 区块
```

### 布局速查表

一个页面通常混合 3–5 种布局。每种布局的线框图、内容约束、易错点、对应 CSS 类名见 `references/layouts.md`——**选定布局后只看该布局对应的一节，不需要通读整份文档**。

| # | 布局名称 | 适用内容 | 关键词触发 |
|---|---------|---------|-----------|
| A | 纯文卡片 | 段落文字、说明、简介 | "介绍"、"说明"、"背景" |
| B1/B2 | 双栏图文 | 图文配合，Zigzag 交替 | "配图"、"如图所示" |
| C | 数据展示行 | 统计数字、指标 | "数据"、"指标"、"成果" |
| D | 时间线/议程表 | 发展历程、大事记、议程 | "历程"、"大事记"、"议程" |
| E | 图片画廊 | 多张图片并列 | "照片"、"风采"、"集锦" |
| F | 列表卡片 | 并列条目 | "列表"、"要点"、"服务" |
| G | CTA 区块 | 报名、联系方式 | "报名"、"联系"、"参与" |
| H | Tab 导航 | 栏目标签切换 | 推荐，用户说不需要时省略 |
| I | 新闻列表行 | 标题+日期条目 | "新闻"、"资讯"、"动态" |
| J | 焦点区 | 左大图+右新闻列表 | "头条"、"焦点"、"要闻" |
| K | Hero 轮播 | Header 区多图轮播 | "轮播"、"滚动banner"、"幻灯片" |
| L | 内容区滑动 | 水平滑动图片/卡片 | "滑动"、"左右滑"、"横滑" |
| M | 两栏并排 | section 内左右并排，含 twin-sections | "双栏"、"两栏等宽"、"双栏并排" |

### 区块排列原则

典型顺序：**Header → Tab 导航 → 概述(A/B) → 焦点区(J)或核心数据(C) → 详细内容按主题展开 → 时间线/历程(D) → CTA(G)**。核心原则是**信息从概括到具体，视觉从重到轻**。

**页面布局最低要求**（规划阶段自检，不满足则调整）：

- ✅ 至少一个**带图区块**：B（双栏图文）、F（上图下文卡片）、E（画廊）、L（滑动）、J（焦点区）、K（Hero 轮播）——六者至少有其 一。纯文字卡片(A)和纯文字新闻列表(I)不计入。
- ✅ 至少一个**多栏区块**：B（双栏图文）、J（焦点区）、M（两栏并排/twin-sections）——三者至少有其 一。全页从头到尾单列纵向堆叠视为不合格。
- ⚠️ **豁免**：纯文本文档型页面（法规全文、公告通知、纯政策说明），经规划表中明确标注"纯文档型，豁免分栏"后可忽略以上约束。

**允许的调整**：合并相邻同类区块、省略不适用的区块、交换 C/J 位置、在任意位置插入新闻列表(I)。

**不允许**：把时间线(D)放在概述之前；在传统 CMS 模式中把所有模块都做成白卡悬浮在灰底上；把页面做成 SaaS landing 或 App dashboard。

**Section/Module 节奏规则**：相邻模块原则上应变换布局类型（A→B→F→I→D 合格，A→A→F→F 需要理由），用两栏消化横向空间、减少留白、打破视觉单调。传统 CMS 模式优先使用模块框、栏目标题线和边框分隔；现代分段式页面才使用大面积交替底色。

**例外条款**：当内容本身就是多条**同类并列信息**（比如连续 5 条新闻、连续 4 个数据模块）时，不必为了"变化"而强行拆成不同布局——那样反而割裂了信息的整体性。这种情况下允许连续使用同一布局，但要通过**列数、卡片密度、是否带图**等参数变化制造视觉差异（例如两组数据展示行分别用 3 列和 4 列）。判断标准：如果拆分会让读者以为这是两类不同的信息，就不该拆。实现时在当前重复的 section 上显式标注 `data-layout-repeat="true"`，否则校验脚本会按基础布局字母阻断（如 `M` 与 `M-twin`、`F-cols3` 与 `F-cols4` 仍视为同一布局家族）。

**图片优先**：参考页面均以图片为主导，而非大段文字。每个区块应优先考虑带图的布局——双栏图文(B)、卡片(F-上图下文)、画廊(E)、焦点区(J)、滑动(L)。纯文卡片(A)仅用于概述和简短说明，不应连续出现多个。

### 反 AI 感对照表（否决项，不是加分项）

生成后如果发现左列特征，必须修改，不能因为"能跑"就放过：

| 类别 | AI 味（避免） | 正确做法 |
|------|-------------|---------|
| 圆角 | `border-radius: 8-16px` 大圆角卡片/按钮 | 分场景：图集/政务 0px，信息卡 2–4px，内容区图片 4–6px，文旅/gallery ≤8px |
| 阴影 | `box-shadow` 弥散阴影、悬浮卡片 | 用 `border: 1px solid` 细边框代替阴影 |
| 渐变 | 按钮/标题大量使用渐变 | 纯色为主，渐变仅用于 Hero 背景 |
| 按钮 | 大圆角、渐变填充、hover 上浮效果 | 纯色背景、小圆角(2-4px)、无动效或仅变色 |
| 间距 | 段落和 section 间大量留白 | 紧凑密度（见第五节），内容为主 |
| 配色 | 安全蓝(#3B82F6)、紫色渐变、低饱和莫兰迪 | 从主题推导主色，见第四节，色感更鲜明 |
| 字体 | 系统默认栈，全页统一字号 | PingFang SC / Microsoft YaHei，标题有大小对比 |
| 卡片 | 白色卡片浮在灰色背景上 | 卡片与背景同色或接近，仅用细边框分隔 |
| emoji | 🔴📅🎯✨📧 等装饰性 emoji | **严格禁止**。用 CSS 形状（`◆``●``▸`）、内联 SVG、或纯文字标记替代 |
| 图标 | 鲜艳的 SVG 图标库 | 如需图标，用 CSS 绘制或简单几何 SVG，颜色用 `--color-*` 变量 |
| 玻璃拟态 | `backdrop-filter: blur()` 毛玻璃卡片 | 传统 CMS 页面不使用玻璃拟态，用实色背景 |
| 异形背景 | 不规则色块、波浪、斜切背景 | 背景统一用纯色或渐变；仅榜单长条海报等配方明确要求的局部主视觉可用斜切色带 |
| 装饰过载 | 多种民俗/节庆元素同时堆砌 | 选 1–2 种克制使用，宁少勿多 |
| 正文过大 | body 默认 16px 显得松散 | 正文 14–16px，紧凑场景用 14px |

## 四、强制显式选择（避免"千篇一律"的核心机制）

以下几个维度都存在"最省事的默认值"。**要求：生成前在内部用一句话明确本次选择依据**，而不是让它落入默认值。最终交付如果只能返回 HTML，不要把这些说明文字输出到 HTML 之前或之后。

### 标题变体（四种，全页统一一种，特殊区块可例外）

| 页面气质 | 推荐变体 |
|---|---|
| 传统 CMS 门户/政务/会议 | 0D CMS 横线标题 |
| 榜单/强栏目感 | 0C 色块标题条 |
| 常规信息/介绍类（默认，但仍需主动确认） | 0A 左色条 |
| 纪念/品牌主张/文旅 | 0B 居中装饰短线 |

### Header 形式

| 素材情况 | 推荐 Header |
|---|---|
| 有 2 张以上可用/可生成的场景图 | 布局 K：Hero 轮播 |
| 有 1 张用户提供的完整设计 KV/海报图 | `.kv-banner` 或 `.hero--poster-image`，保持整图不裁切 |
| 有 1 张 AI 生成或搜索导入的无文字场景图/视觉底图 | 静态大图 hero + 遮罩(`.hero--gradient` 之外的真实图片变体)，标题用 HTML/CSS 叠加 |
| 无图、纯文字型、极简风格 | `.hero--minimal` 或 `.hero--gradient` 几何渐变 |

**Header 信息容量**：Header 只承载页面主标题、短口号和必要视觉信息。主标题最多控制在 2-3 行；当中文标题超过约 24-28 个字符，或包含“暨/及/与/——”等复合标题结构时，优先拆成短主标题 + 副标题/说明。时间、地点、主办单位、承办单位等会务信息移到首个内容模块或独立信息条，不要全部塞进 Hero 面板。

**英文副标题**：英文副标题仅在页面标题较短、品牌感/国际化感明确、且不会挤压中文主标题时使用；长中文会议标题默认不加英文副标题。

### 卡片圆角（按场景强制区分，不能全页统一成一个"看起来安全"的数值）

图集/政务 `0px` ｜ 信息卡 `2–4px` ｜ 内容区图片（B/J/L 布局中的配图）`4–6px` ｜ 文旅/gallery `≤8px`。

### 图片比例与图文垂直对齐（双栏/焦点区/卡片等含图布局）

`base.css` 中图有默认比例（B 布局 `4/3`、J 布局 `16/10`、F 卡片 `3/2`），B 布局图默认占行宽 40%。**这些比例和宽度必须根据实际图片内容和文字量重新评估，不能直接用默认值**：

| 图文关系 | 图比例建议 | 图宽度（B 布局） | 垂直对齐 |
|----------|----------|-----------------|---------|
| 文多图少（文字量充足，图仅辅助） | `4/3` | 40%（默认） | `align-items: center`（图文并茂） |
| 图文均衡 | `3/2` | 40%（默认）或 35%（`.row--tight`） | `align-items: center` |
| 文少图多（文字仅 1–2 段，图是主体） | `3/2` 或 `16/9` | 35%（`.row--tight`）或 30%（`.row--compact`） | `align-items: flex-start`（`.row--top`，文顶对齐不悬空） |

**判断标准**：文字区域的高度是否 ≥ 图片高度的 70%。是 → `center` 居中；否 → `.row--top` 顶对齐 + 更扁的图比例 + 缩窄图宽度。三者可以组合使用（如 `.row--top.row--compact`）。

**实测参考**：1200px 容器中 3 段文字约 157px 高。若图 40% 宽 + 3:2 比 → 图高 309px → 空白 152px（49%）。缩至 30% 宽 + 16:9 比 → 图高 196px → 空白仅 39px。

### 配色防重复规则

生成前在内部陈述本次选定的**主色色相角度**和**明暗基调**（例如"主色色相约 200°、浅色基调"）。如果这与当前对话可见历史中已经生成过的专题页色相接近（差值 <20°）或直接复用了 `references/color-system.md` 里方向参考的整组 hex 值，必须重新推导，调整饱和度、明度、辅色或标题/导航处理——配色推导算法与方向参考见 `references/color-system.md`。

> **本节不是封闭列表。** 以上覆盖了最高频的"不假思索就用默认值"的出事点。在规划阶段，如果发现其他 CSS 默认值（列数、gap、对齐方式、滑动卡片宽度等）可能与本次内容的**数量或篇幅**不匹配，同等地需要显式选择并记录依据。核心原则：**CSS 中的每一个默认值在被"用上"之前，都必须被"审视过"是否适合本次内容。**

## 五、留白与紧凑度

密度由**内容性质**决定，推荐默认"紧凑"档以贴近参考页面的信息密度；用户说"大气/透气"时才降为"标准"或"宽松"。紧凑档仍保留 `max-width:1200px` 上限——全宽通栏在超宽屏（>1440px）上文本行过长、可读性差，间距密与宽度无上限是两回事。

**关于"紧凑 ≠ 全宽"**：紧凑控制的是间距密度（间距小、留白少、信息密度高），不是让文本行拉到无限宽。1200px 是文本可读性的天花板——超过此宽度的屏幕，内容居中、两侧留白，而非无限制拉伸。

| 内容性质 | 密度档 |
|---|---|
| 纪念/宣传/叙事/品牌主张 | 宽松 |
| 介绍/说明/常规信息聚合 | 标准 |
| 会议/活动/议程/数据/榜单/资讯流 | 紧凑 |

三档具体数值（`--space-section`/`--space-card`/`--space-gap`/`--leading`/`--max-width`/`--font-size`）已写入 `assets/base.css` 的 `:root` 注释中，直接取用，不需要在这里重复记忆。

## 六、生成流程（避免半成品与代码错误）

**不要一次性从头到尾直接吐出完整 HTML。** 按以下阶段推进，每个阶段做完再进入下一步：

1. **需求归类**：把上游简报或口语化摘要归类为页面类型（会议/政务/门户/文旅/公益/纪实/榜单等），读取 `references/page-type-recipes.md` 对应配方；若用户给了截图/链接，先按第一节的视觉盘点项提取风格规律。
2. **规划**：先在内部形成一张 Section/Module 规划表（除非用户要求解释，否则不长篇输出），列出：`id`、选用布局字母、页面壳类型、标题变体、是否含图片、图片来源策略、密度档位、主色色相。这一步让结构性冲突在写代码前暴露，而不是写到一半发现要推倒重来。
3. **获取首屏资产**：凡是首屏强视觉页面，写 HTML 前必须按 `references/image-assets.md` 自探测图片生成工具并尝试生成或导入 Banner/KV，记录内部结果：`targetSlot`、`ratio/size`、`toolUsed`、`assetPath`、`fallbackReason`。如果成功获得资产，后续 Header 必须引用该路径。
4. **确定视觉系统**：按第四节把标题变体、Header 形式、圆角、配色都显式选定，写入 `assets/base.css` 复制出来的 `:root` 变量。**直接复制 `assets/base.css` 全文再改数值，不要凭记忆重新敲写这份 CSS**——转述长代码是产生遗漏和语法错误的主要来源。
5. **搭建骨架**：以 `assets/base.html` 为起点填充 Header/Tab/Footer。传统 CMS 页面使用 `.topic-shell` + `.module-box`；现代分段式页面才直接使用 `.section`。每个 `<section>` 标签除了 `id` 之外，加上 `data-layout="X"` 属性（X 为布局字母，允许带后缀如 `M-twin` 区分同布局的不同形态），例如 `<section id="agenda" data-layout="D">`——这个属性纯粹用于后续自动校验，不影响样式。
6. **填充内容**：按规划表逐个 section 落地，需要 Tab 导航或轮播时从 `assets/tab-nav.js` 复制对应逻辑，不要重新实现。
7. **静态自检（不能跳过）**：有文件系统和 Python 时，运行 `python3 scripts/validate_page.py <生成的html路径>`。它会检查锚点完整性、禁用元素、相邻 section 是否重复布局、section 是否缺 id/data-layout、默认色值、首屏强视觉页面是否缺真实 Banner 等可编程校验项目；其中强视觉缺 Banner 属于启发式 WARN，图片策略最终以 `references/qa-checklist.md` 的人工确认和浏览器渲染为准。**校验脚本报错时定位到具体行修复后重新运行，不要因为"大体能看"就跳过报错项。** 如果宿主只允许返回 HTML 字符串、没有脚本执行工具，则按同一规则人工检查，并且不得声称“已运行脚本”。装饰性 emoji 脚本只做 WARN，人工清单仍按否决项处理。
8. **渲染验收**：有浏览器/Playwright 时，按 `references/qa-checklist.md` 打开桌面和移动端视口，确认 Banner 加载、首屏非空、导航可用、图片不变形、文字不重叠、移动端多栏正确折叠。
9. **收尾**：确认 Banner 图片策略已按要求执行（已使用用户/项目素材、已生成/导入，或已因明确原因回退为 CSS 占位），且最终 HTML 没有输出内部工具判断注释。
