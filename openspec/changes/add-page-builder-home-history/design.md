## Context

`page-builder` 当前首页只提供一个极简启动入口，代码集中在 [`apps/page-builder/src/renderer/pages/HomePage.tsx`](/Users/liu/Documents/work/learning/Proma/apps/page-builder/src/renderer/pages/HomePage.tsx)。该页面已经有稳定的文案、视觉和输入行为，且用户明确要求：

- 历史记录必须拆为独立组件开发，不能继续把全部逻辑堆在首页单组件里
- 首页现有样式和布局不能被重写，只能在现有对话框下方增量追加内容
- 历史记录的样式必须与首页现有风格保持一致，并优先参考现有 `taste-skill` 的设计约束

同时，现有数据层已经具备构建历史记录的大部分基础：

- 工作区可通过 `listWorkspaces()` 获取，并带有 `template: 'page-builder'`
- 会话可通过 `listSessions()` 获取，且 `updatedAt` 更接近“最近活跃时间”
- 工作区预览可通过现有 `preview-state` / `preview` 路由获取

但现有后端并没有一个“page-builder 项目”概念的聚合接口，删除能力也存在明显边界：

- 普通工作区删除接口会拒绝删除仍有会话的工作区
- `deleteAgentWorkspace()` 当前仅移除工作区索引项，不负责级联清理会话和工作区根目录

因此，这个需求虽然是首页增强，但本质上是一个跨前后端的 page-builder 项目恢复与生命周期补全。

## Goals / Non-Goals

**Goals:**

- 在不重写首页现有 hero 区的前提下，于其下方新增历史记录区域
- 以独立组件形式承载历史记录 UI、交互和数据加载
- 让历史记录区延续首页现有视觉语言，而不是形成独立的卡片产品风格
- 将每个 `page-builder` 工作区作为一个历史卡片展示，并提供 `iframe` 预览
- 让卡片支持 `预览`、`编辑`、`删除` 三个产品级动作
- 为 page-builder 项目提供安全的级联删除链路
- 让历史排序体现“最近活跃项目”，而不是简单创建顺序

**Non-Goals:**

- 不重做首页现有对话框、标题、背景动画或输入区视觉
- 不为历史记录区引入与首页割裂的新视觉体系
- 不为普通工作区引入新的历史卡片入口
- 不引入截图生成、封面缓存或项目标签等新的媒体元数据系统
- 不改变普通工作区删除语义或把其扩展为通用级联删除
- 不在本次变更中重构 builder 页面或预览服务本身

## Decisions

### 1. 历史记录以 page-builder 工作区为主实体，而不是以会话为主实体

首页卡片将以 `template === 'page-builder'` 的工作区作为唯一数据源主体。卡片上的“编辑”行为默认恢复该工作区最近一次会话；若工作区下没有可用会话，则即时创建一个新会话再进入 builder。

这样建模与当前产品入口一致：用户创建的是“项目工作区”，而不是一条独立会话。历史卡片也因此能天然承载删除整个项目的语义。

备选方案：

- 以会话为卡片主体。放弃原因是用户认知会退化成“聊天历史”，与 page-builder 的项目语义冲突，且无法自然承载项目级删除。

### 2. 首页仅挂载独立历史区组件，现有首页 hero 区保持原样

`HomePage` 继续保留现有启动逻辑、现有错误处理和现有 DOM 结构；新增内容以独立组件形式挂载在对话框区域之后，例如：

- `PageBuilderHistorySection`
- `PageBuilderHistoryCard`
- `usePageBuilderHistory`

实现上，首页现有 copy / panel / error 相关节点的样式类与层级不做重写；历史区只作为其下方的新 sibling 区块存在。这样可以满足“独立组件开发”和“禁止修改现有首页样式布局”的双重约束，同时把后续列表状态、卡片 hover、删除确认等复杂交互从首页主组件中隔离出去。

备选方案：

- 继续在 `HomePage.tsx` 内直接追加列表状态和卡片渲染。放弃原因是会快速把首页变成数据、交互、删除逻辑混合的大组件，与用户约束直接冲突。

### 3. 历史列表使用 page-builder 专用聚合接口，而不是前端拼接多个通用接口

后端新增 page-builder 专用项目摘要接口，由服务端完成以下聚合：

- 过滤 `template === 'page-builder'` 的工作区
- 关联该工作区最近一次会话
- 解析用于卡片预览的 `previewUrl`
- 计算“最近活跃时间”并完成倒序排序

前端首页只请求一份聚合后的项目摘要列表，而不是自己依次调用：

- `listWorkspaces()`
- `listSessions()`
- 对每个工作区继续调用 `getWorkspacePreviewState()`

选择服务端聚合的原因：

- 避免首页形成明显的 N+1 请求
- 排序规则在服务端统一，更容易复用到后续入口
- 可以顺便把“最近会话缺失”“无预览”等边界转换成稳定字段，而不是让前端到处判断

备选方案：

- 前端直接组合现有三个接口。放弃原因是首页请求会随项目数线性膨胀，且编辑入口、排序、空状态逻辑会分散在前端组件内。

### 4. 历史区视觉必须延续首页现有语言，并优先参考 taste-skill

历史记录区虽然作为独立组件开发，但视觉上仍然属于首页的一部分，因此其卡片边框、层次、背景处理、动效强度与交互密度都需要延续现有首页语言，而不是额外引入另一套 gallery 风格。实现时应优先参考当前工程内已有的 `taste-skill` 设计约束，让新增卡片在精致度上提升，但不破坏首页既有气质。

这意味着：

- 历史区的容器与卡片样式需要与首页现有浅色、轻层次、微动效风格兼容
- hover 态与操作蒙层需要克制，不能喧宾夺主压过顶部启动入口
- 不通过重写首页 hero 区样式来“顺便统一”，而是让新组件主动贴合现有语言

备选方案：

- 把历史区设计成独立模板市场式风格。放弃原因是会让首页出现明显视觉割裂，也违背了用户要求。

### 5. 卡片预览直接复用现有 workspace preview 路由，并使用 iframe 懒加载

卡片中的网页缩略预览不引入新的截图管线，直接复用当前工作区预览入口，通过 `iframe` 加载。卡片级实现采用以下策略：

- `loading=\"lazy\"` 或等价的视口惰性加载
- 覆盖交互蒙层，避免用户直接点击 `iframe` 内容
- 没有预览入口时展示统一的空态预览壳，而不是继续加载旧地址

这样可以最大限度复用已有 `page-builder-live-preview` 产物，同时控制首页同时加载多个预览页面时的成本。

备选方案：

- 为首页生成静态截图缓存。放弃原因是需要额外的截图、缓存失效和文件存储机制，明显超出本轮需求范围。

### 6. 卡片底部信息固定为工作区名和创建时间，排序按最近活跃时间

卡片底部只展示：

- 工作区名称
- 工作区创建时间

但列表排序不依据 `createdAt`，而依据“最近会话更新时间”，因为当前工作区 `updatedAt` 主要在重命名等管理动作时变化，无法准确表达网页项目是否最近仍在编辑。

这样可以同时满足用户对卡片底部信息简洁的要求，以及首页作为“继续工作入口”的实用性。

备选方案：

- 按工作区创建时间排序。放弃原因是旧项目只要持续在迭代，也会被挤到后面，和“历史记录”作为恢复工作入口的目标不一致。

### 7. 删除能力采用 page-builder 专用级联删除服务，不修改普通工作区删除语义

后端新增 page-builder 项目删除服务，由其显式完成：

- 校验目标工作区存在且模板为 `page-builder`
- 找出该工作区下全部会话并逐个删除
- 清理会话消息文件和 session 工作目录
- 清理该工作区根目录，包括 `workspace-files`
- 最后移除工作区索引项

这一能力应通过 page-builder 专用路由暴露，而不是直接改变普通 `DELETE /api/workspaces/:id` 的行为。这样能把“级联删除项目”限制在 page-builder 这个产品语义下，避免普通工作区管理被意外升级为破坏性更强的删除模型。

备选方案：

- 扩展通用工作区删除接口为级联删除。放弃原因是会改变现有全局工作区删除契约，影响面过大。

### 8. 编辑动作优先恢复最近会话，缺失时自动补建新会话

历史卡片的“编辑”动作需要稳定可达，因此后端聚合结果应返回最近会话 id；若某个 page-builder 工作区没有会话，则前端在点击编辑时为其创建一个新会话，再进入 builder。

这样可以兼容历史数据异常、手动清理过会话、或后续维护场景，而不会让首页出现“看得到项目但打不开”的死卡片。

备选方案：

- 没有会话时直接禁用编辑按钮。放弃原因是会把缺失会话的修复责任推给用户，体验较差。

## Risks / Trade-offs

- [多个 iframe 预览同时加载导致首页变重] → 使用惰性加载、统一卡片尺寸和交互蒙层，避免首屏一次性激活全部预览
- [首页新增历史区后整体内容高度增加，弱化原本的居中首屏感] → 不改现有 hero 区内部结构，只让历史区作为下方追加内容，并接受页面变为可滚动首页
- [历史区卡片容易因为功能增强而偏离首页风格] → 将“延续首页视觉语言并优先参考 taste-skill”写入设计约束与验收任务，而不是留给实现阶段自由发挥
- [删除项目的破坏性较强] → 删除前必须有明确确认，并将级联范围限定为 page-builder 工作区
- [服务端新增聚合接口带来新的投影结构] → 保持返回字段最小化，只暴露首页卡片真正需要的字段，避免形成第二套通用 workspace API
- [旧 page-builder 工作区可能没有预览或没有会话] → 卡片空态与编辑补建策略都在设计中显式支持，不把历史数据完整性作为前提

## Migration Plan

1. 新增 page-builder 项目摘要与删除能力的后端服务和 HTTP 路由。
2. 在前端 API 层增加 page-builder 首页历史记录所需的专用请求方法。
3. 新增独立历史区组件及其卡片子组件，在首页对话框下方挂载，不重写现有 hero 区，并让历史区视觉贴合首页现有风格。
4. 为项目无预览、无会话、删除确认、删除后刷新列表，以及历史区视觉一致性场景补齐测试。

回滚策略：

- 前端回滚时移除首页历史区挂载即可，现有首页启动链路不受影响
- 后端回滚时删除 page-builder 专用聚合与删除路由，不影响现有通用 workspace / session 路由
