## Context

当前 `feature/proma-web` 已经从原工程中裁剪出以 Agent 会话、工作区运行时和 Web 界面为中心的产品形态，代码结构与 `origin/main` 在 2026-03-15 之后已经明显分叉。上游这段时间新增的候选提交里，只有一部分仍直接作用于当前主路径：

- `b8a11dd`: 调整流式文本渲染节奏，并在流式期间禁用 `content-visibility`
- `ae0c450`: 将 SDK 登录类技术错误转换为用户可理解的消息
- `550d85f`: 升级 `@anthropic-ai/claude-agent-sdk` 到 `0.2.76`

与此同时，上游 `0b6dbc2` 等修复依赖旧 `chat` 配置链路，而当前分支已无对应的生产消费者，因此不应回迁。

本次变更是一个跨 renderer / packages / main runtime 的兼容性回迁：它既涉及前端流式渲染体验，也涉及后端错误语义和 SDK 版本边界，因此需要先形成统一设计，再进入实现。

## Goals / Non-Goals

**Goals:**
- 将上游仍对当前 Agent 产品有效的运行时修复回迁到当前分支，而不回退当前工作区与 UI 定制。
- 恢复稳定、渐进、无明显跳变的流式文本体验，避免旧中间态方案重新引入卡顿或结尾突变。
- 让已知 SDK 登录/认证类错误以用户可读形式展示，而不是直接暴露技术性原文。
- 以受控方式评估 SDK 升级，仅在验证确认必要且无冲突时纳入。
- 明确冲突处理原则：凡是与当前产品定制冲突的行为变更，暂停并交由用户确认。

**Non-Goals:**
- 不回迁仅作用于旧 `chat` 模式、工具配置面板或无生产消费者代码的修复。
- 不将上游 2026-03-15 期间已经被后续修正的中间态流式方案逐提交照搬进来。
- 不借本次 change 做额外 UI 重构、工作区交互重设计或无关的性能治理。
- 不承诺一定升级 SDK；升级是评估项，不是无条件执行项。

## Decisions

### 1. 以“行为兼容移植”替代逐提交 cherry-pick

**Decision**
- 本次回迁以当前分支代码为基础，提炼上游提交的最终有效行为，再按现有结构做兼容性移植。

**Rationale**
- `ae0c450` 所在的上游代码仍基于旧渠道 / 模型体系，而当前分支已切换为环境变量与现有 Agent 运行时配置路径；直接 cherry-pick 会把无关结构差异一起带入。
- `b8a11dd` 修正的是上游先前 `211a613` / `90fdd19` 的中间态方案，逐提交引入会把已被否定的实现绕一圈重新带回来。
- 当前分支已经有工作区作用域运行时、会话隔离和 UI 定制，兼容移植能把风险控制在功能面而不是提交面。

**Alternatives considered**
- 逐个 cherry-pick 上游提交：保留提交历史，但冲突面更大，也更容易把旧链路实现带入当前分支。
- 全量 merge `origin/main`：成本过高，且会破坏当前已建立的产品边界。

### 2. 流式输出只迁移上游“最终行为”，不引入双缓冲中间方案

**Decision**
- 以 `b8a11dd` 为目标行为基准，回迁“平滑渐进输出 + 流结束渐进排空 + 流式期间禁用 `content-visibility`”这组最终行为。
- 不单独回迁 `211a613` 的双缓冲 / 固定节拍 setState 方案，也不单独保留 `90fdd19` 的流式期间 `content-visibility` 优化。

**Rationale**
- 当前分支的 [useSmoothStream.ts](/Users/liu/Documents/work/learning/Proma/packages/ui/src/hooks/useSmoothStream.ts) 仍是较早实现，存在“流结束后一次性 dump 剩余队列”的行为，和上游最终修复目标不一致。
- 上游最终方案已经明确否定“流式期间启用 `content-visibility`”与“双缓冲节拍刷新”这两个中间状态，因此应直接对齐最终行为，而不是重复引入再回退。
- 当前产品主路径主要在 Agent 消息流，因此回迁应优先保证 Agent 渲染链路稳定；若上游同时修改了 chat 组件，则只提取当前仍有消费者的共性逻辑，例如 `useSmoothStream` 和 `message.tsx` 的 Markdown/render 稳定性优化。

**Alternatives considered**
- 仅替换 `useSmoothStream` 算法、不处理 `content-visibility`：实现简单，但无法消除“渲染层优化与流式体验相互干扰”的问题。
- 直接采用 `211a613`：理论性能更优，但上游已经用后续提交证明其在真实流式体验上不合适。

### 3. 错误友好化放在运行时错误出口的共享位置，而不是复制上游旧渠道逻辑

**Decision**
- 在当前 Agent 运行时的共享错误出口引入“原始错误 -> 友好提示”的映射函数，并同时覆盖适配器事件流错误与 orchestrator 终态错误。
- 映射规则初期仅覆盖已确认有效的登录/认证类错误模式，未命中的错误继续透传原文。

**Rationale**
- 当前分支的错误展示已经通过 `callbacks.onError(...)` 与 `status` 消息持久化汇聚到统一出口，适合放置一个小型、可扩展的映射层。
- 上游 `ae0c450` 的具体接入点依赖旧渠道系统，不能直接照搬，但“将 SDK 特定错误模式转换为用户语言”的思想仍然成立。
- 先做白名单式已知模式映射，能降低误伤风险，避免把调试价值较高的未知错误全部模糊化。

**Alternatives considered**
- 只在 renderer 层包装错误文案：实现表层化，但会导致 JSONL 持久化与 SSE 实时展示出现不同文案。
- 直接替换所有认证相关错误：覆盖面大，但容易吞掉仍需保留的底层诊断信息。

### 4. SDK 升级作为已确认范围，完成依赖更新后做受控回归

**Decision**
- 按最新确认范围，将 `@anthropic-ai/claude-agent-sdk` 从 `0.2.71` 升级到 `0.2.76` 纳入本次 change。
- 升级后仍必须满足以下条件才算完成：
  - `typecheck`、`test`、`build`、关键对话路径回归全部通过
  - 未引入与当前工作区运行时、MCP、会话恢复链路相冲突的新行为

**Rationale**
- 你已明确要求本次回迁必须包含 SDK 升级，因此不再停留在“是否需要”的评估态。
- 上游该版本窗口包含 MCP / 模块解析修复，与当前产品的工作区运行时和 Agent 路径直接相关，属于值得一起收敛的运行时边界。
- SDK 升级仍然是高风险变更，所以实施方式仍保持“先升级，再做全量验证，不通过就继续修复”的受控路径。

**Alternatives considered**
- 保持 `0.2.71`：已不满足当前确认范围。
- 后续另开 change 单独升级：隔离性更强，但会把同一轮回迁的运行时边界拆散，不符合当前要求。

## Risks / Trade-offs

- [流式平滑策略迁移后仍出现节奏异常] → 通过针对 `useSmoothStream` 的单元测试和实际多轮流式回归验证“渐进输出、结尾不跳变、切会话不串流”。
- [移除流式期间 `content-visibility` 带来长对话渲染回退] → 保留“仅在非流式阶段启用”的策略，并把 Markdown 组件稳定引用优化作为补偿。
- [错误友好化过度概括，掩盖真实故障] → 仅匹配白名单错误模式；原始错误继续保存在日志 / `errorOriginal` 中。
- [SDK 升级影响会话恢复、MCP 或工作区运行时] → 升级后通过专项回归定位并修复，不再以“放弃升级”作为默认出口。
- [上游逻辑与当前 UI / 工作区定制冲突] → 不在设计阶段拍板，实施时发现冲突立即暂停并让用户确认。

## Migration Plan

1. 为 `agent-conversation` 编写 delta spec，先把流式行为和错误可读性要求固化下来。
2. 基于当前分支代码结构移植流式修复：先更新共享 `useSmoothStream` 行为，再处理 Agent 消息渲染层与 `message.tsx` 的渲染稳定化。
3. 在 main runtime 中接入错误友好化映射，确保实时错误、持久化错误消息和前端展示语义一致。
4. 升级 SDK `0.2.76`：更新依赖、跑全量校验、做关键对话回归；若出现回归则在同一 change 内继续修复直至通过。
5. 完成后执行 `typecheck`、`test`、`build` 与 Playwright 对话回归，确认当前工作区运行时和定制 UI 未被破坏。

**Rollback strategy**
- 流式修复与错误映射均为本地代码调整，可逐文件回退。
- SDK 升级如发现阻塞性不兼容，需要先记录冲突点并重新决策；当前默认目标不是回退，而是修复后保留升级。
