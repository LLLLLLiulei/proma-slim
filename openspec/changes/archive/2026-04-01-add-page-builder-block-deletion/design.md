## Context

当前 `page-builder` 已经有一条稳定的“选中区块 -> 工具条动作 -> 后端 HTML 回写 -> preview revision 刷新”的直接编辑链路：
- 预览 bridge 会把当前选中的 DOM 元素解析为唯一 `selector`，并在选区失效或预览重载时主动清空状态。
- 前端工具条已经承载了 CMS 入口和图片替换入口，说明“围绕已选区块触发局部操作”这条交互路径已经成立。
- 主进程已经证明可以通过解析 `workspace-files/index.html` 并回写，再通过 preview revision 让 Builder 显示最新结果。

删除功能与图片替换、内联文本编辑属于同一类“对明确选中目标进行直接修改”的操作，但它是破坏性动作，不能像普通按钮一样即点即生效。这里的设计重点不是“怎么从 DOM 删除节点”，而是如何明确删除目标、如何控制误删，以及如何让删除后选区、工具条和预览状态保持一致。

第一版最重要的约束是：当前系统里的“区块”仍然等价于“当前选中的 DOM 元素”，而不是更高层的语义化 block schema。因此删除语义必须与当前选区语义保持一致，否则会出现“点中了标题却删掉整张卡片”这类难以预测的结果。

## Goals / Non-Goals

**Goals:**
- 在已选区块工具条中启用 `删除` 动作，并通过二次确认防止误删。
- 明确第一版删除语义为“删除当前选中的 DOM 元素本身”，沿用现有唯一 `selector` 作为后端定位依据。
- 让删除成功后的结果继续走 `workspace-files/index.html` 回写与 preview revision 刷新链路。
- 删除成功后清空当前选区并移除工具条；删除失败时保留当前选区并反馈错误。

**Non-Goals:**
- 不自动推断“更合理的父级语义块”并上提删除目标。
- 不实现撤销、回收站或历史版本恢复。
- 不在第一版中清理删除节点关联的静态资源文件，例如图片、音频或其他附件。
- 不新增独立的预览内删除手势或键盘快捷键。

## Decisions

### Decision: 删除目标固定为当前选中的元素本身，不做父级提升

**Decision**
- 删除请求只携带当前选区的唯一 `selector`。
- 后端删除逻辑以 `selector` 唯一命中的元素作为删除目标，直接执行 `remove()`。
- 不引入额外的删除目标描述符，也不在 bridge 层做“自动找父块”推断。

**Rationale**
- 当前 Builder 的选区语义已经稳定地建立在“选中的就是当前目标元素”之上，删除如果改成别的语义会破坏用户预期。
- `selector` 足够表达删除目标，不像图片替换那样需要在块内继续解析子节点目标。
- 省略父级提升和多级推断，可以显著降低误删范围和后端歧义。

**Alternatives considered**
- 自动删除父容器或语义块：更像“删整个卡片”，但会让行为不透明，误删成本更高。
- 让 bridge 同时回传“删除推荐目标”：会引入新的推断规则和解释成本，第一版没有必要。

### Decision: 二次确认使用现有 AlertDialog，而不是工具条内联确认

**Decision**
- 点击 `删除` 后，由 Builder 页打开现有样式体系下的 `AlertDialog` 确认框。
- 用户点击确认按钮后才真正发起删除请求；取消时关闭确认框但保留当前选区。

**Rationale**
- 删除是破坏性操作，模态确认比贴近工具条的二次点击或 popover 更稳，更不容易误触。
- 项目内已有 AlertDialog 组件与测试模式，复用成本低且视觉一致。
- 一旦删除成功，原锚定元素会立即失效，使用独立模态可以避免锚点本身消失导致的交互抖动。

**Alternatives considered**
- 原生 `window.confirm`：实现简单，但风格不一致、可测试性差。
- 工具条按钮二次点击确认：交互更轻，但误触风险更高，也不利于放置破坏性说明文案。

### Decision: 删除动作在有选区时始终可见，不依赖额外能力声明

**Decision**
- 只要当前存在合法选区，工具条就展示 `删除` 动作。
- 不额外让 bridge 回传“supportsDelete”能力元数据。

**Rationale**
- 当前 bridge 已经通过 `BLOCKED_TAGS` 避开 `HTML/BODY/HEAD/SCRIPT/STYLE/META/LINK` 这类不应被选中的节点，因此合法选区本身就已经足够作为删除前置条件。
- 删除不像图片替换那样需要对块内子目标做唯一性推断；目标就是当前选中的元素。
- 少一层能力协议，前后端链路更简单。

**Alternatives considered**
- 让 bridge 额外声明删除能力：在现有约束下价值不高，只是增加协议复杂度。

### Decision: 删除成功后继续复用 preview revision 刷新，不保留旧选区

**Decision**
- 删除成功后后端返回新的 preview state，Builder 沿用现有 revision 流程刷新预览。
- 成功后前端主动清空当前选区和待确认状态，不尝试在新 DOM 中恢复或迁移旧选区。

**Rationale**
- 删除会直接改变 DOM 结构，旧选区天然失效；强行保留只会引入新的锚定不确定性。
- 现有 preview revision 流程已经是 Builder 中最稳定的“最终一致性”机制。
- 用户完成删除后通常也需要重新确认下一个目标，清空选区符合当前工作流。

**Alternatives considered**
- 在删除成功后尝试选中相邻兄弟节点：交互更连续，但规则复杂且可能不符合用户预期。
- iframe 内局部 DOM patch 不刷新：视觉更快，但会额外增加 bridge 和 host 的同步复杂度。

## Risks / Trade-offs

- **[用户误把内部子元素当成整个区块]** → Mitigation: 用二次确认兜底，并在第一版明确删除语义就是“当前选中的元素本身”。
- **[删除后留下未引用的静态资源文件]** → Mitigation: 首版接受资源残留，后续如有需要再做离线清理或垃圾回收能力。
- **[删除请求到达后 selector 已失效或不再唯一]** → Mitigation: 后端拒绝写入并返回失败，前端保留当前选区供用户重试。
- **[删除操作导致页面结构塌陷或样式异常]** → Mitigation: 这是内容作者对结构的真实修改结果，系统只负责精确删除当前目标，不做额外结构修复。

## Migration Plan

1. 在区块工具条中启用 `删除` 按钮，并将点击事件上抛到 Builder 页。
2. 在 Builder 页引入删除确认弹框状态，处理取消、确认、进行中和成功/失败反馈。
3. 在 renderer API 中新增删除区块请求封装，只传 `selector`。
4. 在主进程新增 HTML 区块删除服务与 workspace 路由，基于唯一 `selector` 执行 `remove()` 并返回新的 preview state。
5. 补齐工具条、确认框、删除成功/失败、HTML 回写与 preview 刷新测试。

**Rollback**
- 可以先重新将工具条中的删除按钮回退为禁用态，从而停止前端入口暴露。
- 后端删除路由与服务即便保留，只要前端不再调用，不会影响现有 Builder 工作流。
