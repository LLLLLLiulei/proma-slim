Context

Proma 当前的核心前端应用是 apps/app，它已经具备稳定的工作区、会话、消息流、SSE、权限交互、富文本输入和消息渲染能力，但这些能力主要通过通用 Agent 工作台暴露。此次变更要新增 apps/page-builder，为“用自然语言生成网页”场景提供一个独立入口：首页承担项目启动，builder 页承担网页预览与对话式迭代。

该变更不是要重建一套新的聊天和运行时系统，而是在 apps/app 已有能力之上增加一层更贴近产品场景的页面和初始化封装。用户已经确认 apps/app 主要服务于当前体系，后续不会有新的破坏性变动，因此设计上可以接受直接复用其内部前端模块，而不必先抽取成新的共享包。

当前约束与现状：

  • 后端已有工作区与会话接口，可直接支持“首页创建项目并进入构建页”的链路。
  • apps/app 当前没有前端路由体系，也没有现成的多页面壳；page-builder 需要自行提供最小路由能力。
  • builder 页右侧必须尽量直接复用现有对话框、消息列表和输入区，而不是重写聊天 UI。
  • builder 页顶部语义是“项目名”，对应工作区名称，而不是现有会话标题。
  • 第一阶段只开发首页和 builder 页；左侧预览允许先用 iframe 容器和占位地址，不要求完成真实网页生成与预览回传协议。

Goals / Non-Goals

Goals:

  • 新增 apps/page-builder 应用，并提供首页与 builder 两个页面。
  • 让首页输入在提交后真实创建工作区与首个会话，并进入 builder 页。
  • 在 builder 页实现紧凑型双栏布局：左侧为精简预览 iframe 面板，右侧复用现有 Agent 对话体验。
  • 使用工作区名称作为项目名展示与编辑入口，保持产品语义正确。
  • 保证首页首条需求在进入 builder 后自动发送，且只发送一次，避免刷新或回退造成重复发送。
  • 在不修改现有后端协议的前提下完成页面级集成。

Non-Goals:

  • 不新增新的 Agent runtime、消息存储模型或独立的 SSE 实现。
  • 不重做 apps/app 的侧边栏、标签页、多会话工作台布局。
  • 不在第一阶段实现真实的网页生成结果回传协议、预览地址编排或项目发布能力。
  • 不为了模块边界再额外抽取 apps/app 的现有对话能力到新的共享包。
  • 不引入重量级前端路由框架来支撑只有两个页面的新应用。

Decisions

1. apps/page-builder 直接复用 apps/app 内部模块，而不是先做共享抽取

page-builder 会直接使用 apps/app 现有的前端模块，包括 API、Agent 状态原子、SSE 发送能力、消息视图与输入区。这样可以最大化复用当前稳定的会话系统，避免重写聊天内核和消息流整合逻辑。

Rationale

  • 用户明确要求直接基于现有功能做封装和二次开发。
  • apps/app 被视为稳定底座，可以接受内部模块级复用。
  • 先抽共享包会扩大变更范围，延长实现时间，且对当前目标没有直接收益。

Alternatives considered

  • 先将对话能力抽取到 packages/ui 或新的 shared package：边界更干净，但需要先重构 apps/app，与当前“快速验证 page-builder”目标冲突。
  • 只复用底层输入框和消息原语，重新拼一套 builder 对话层：实现独立，但会重复处理会话、SSE、权限和流式状态。

2. 新应用使用最小路由实现，而不是引入路由框架

page-builder 只需要两个页面：/ 和 /builder/:workspaceId/:sessionId。因此采用基于 window.location.pathname、history.pushState 和 popstate 的最小路由实现即可。

Rationale

  • 页面数量少，路径结构简单。
  • 避免为单一启动流引入额外依赖和配置。
  • 更容易与当前 Vite 单页入口结构保持一致。

Alternatives considered

  • 引入 react-router 一类路由库：功能更完整，但超出当前需求，增加学习和维护面。
  • 完全不使用 URL、只靠内存状态切页：实现最简单，但无法支持刷新后恢复 builder 上下文。

3. Builder 页采用“外层项目壳 + 内层 AgentView”的结构

builder 页右侧不会自定义新的聊天面板，而是在外层渲染项目标题条，在内层继续挂载现有 AgentView。为适配这一场景，AgentView 需要增加最小可配置能力，例如允许隐藏自身 header，使 builder 自己接管顶部区域。

Rationale

  • 现有 AgentView 已覆盖消息列表、输入、停止生成、权限交互、AskUser 和错误态。
  • builder 页顶部的业务语义是项目名，不能直接复用现有会话标题栏。
  • 外层包一层比重写消息区风险更低。

Alternatives considered

  • 直接使用原始 AgentView 不做调整：复用最彻底，但顶部会显示并编辑会话标题，不符合产品语义。
  • 只复用底层消息组件，重建整个右侧面板：灵活，但重复实现过多。

4. Builder 页顶部使用工作区名称作为“项目名”

builder 顶部的标题条展示并编辑工作区名称，初始名称固定为“未命名项目”。这条标题条是 page-builder 自己的项目级 UI，不依赖现有 AgentHeader。

Rationale

  • 该产品场景中的核心实体是“项目”，而不是“某次对话”。
  • 现有后端已经将工作区与会话分离，工作区更适合作为项目容器。
  • 用户明确选择 builder 顶部显示项目名，而不是会话标题。

Alternatives considered

  • 使用现有会话标题作为顶部标题：实现更快，但语义错误。
  • 同时展示项目名与会话标题：信息层级过重，不符合当前紧凑工作台目标。

5. 首页启动流使用真实创建链路，并在 builder 中执行一次性自动发送

首页提交后立即调用现有接口创建工作区和首个会话，再跳转到 builder。首页输入的需求不会在首页发送，而是在 builder 初始化完成后自动作为首条消息发送。为避免刷新或重复进入时重复触发，采用一次性 bootstrap 缓存机制：按 sessionId 暂存初始化 prompt，builder 首次发现当前会话无消息时自动发送，随后立刻清理。

Rationale

  • 用户要求首页回车后进入真实构建流程，而不是只做页面壳。
  • builder 才是实际会话上下文完整的页面，自动发送应在该上下文中执行。
  • 一次性缓存机制可以同时兼顾刷新恢复和幂等性。

Alternatives considered

  • 首页直接发送再跳转：上下文切换复杂，失败时更难回收状态。
  • 进入 builder 后只预填草稿，不自动发送：不符合用户要求。
  • 只用内存变量传递 prompt：刷新后丢失上下文，无法安全防重。

6. 左侧预览区第一阶段只做精简 iframe 面板

预览区只包含 iframe 容器以及“全屏”“新窗口打开”两个操作，不提供复杂的浏览器模拟器、设备切换或多控制条。第一阶段允许 iframe 为空白或使用固定占位地址。

Rationale

  • 当前目标是先完成首页和 builder 页骨架，并打通对话式初始化流程。
  • 用户明确要求预览壳精简，不要重型浏览器模拟 UI。
  • 真实预览地址编排属于后续生成链路能力，不应阻塞当前页面开发。

Alternatives considered

  • 做完整浏览器工具栏和设备切换：视觉更丰富，但超出阶段目标。
  • 不放 iframe，只做静态占位：无法验证后续预览容器的集成方式。

7. 构建配置采用“双别名 + 扩展样式扫描”的方式兼容直接复用

由于 apps/app 内部模块大量使用 @/ 指向其 renderer 根目录，page-builder 需要在 Vite 解析中将 @ 指向 apps/app/src/renderer，同时为自身源码提供独立别名，例如 @page-builder。Tailwind 内容扫描也需要覆盖 apps/app/src/renderer/**/*，以保证复用组件的样式不丢失。

Rationale

  • 这是在保留现有 import 体系前提下复用 apps/app 内部模块的最小代价方案。
  • 避免为了复用而批量改写 apps/app 现有 import。
  • 可以让 page-builder 自身代码与复用代码保持可区分的命名空间。

Alternatives considered

  • 在 page-builder 中重新导出一层所有 apps/app 模块：仍然需要处理内部别名问题，收益有限。
  • 批量修改 apps/app 源码别名：改动面大，风险高。

Risks / Trade-offs

  • [直接依赖 apps/app 内部模块增加耦合] → 接受该耦合作为本次设计前提，并尽量把新增改动限制为非破坏性的最小可配置能力。
  • [builder 自动发送首条消息可能在刷新时重复触发] → 使用按 sessionId 存储的一次性 bootstrap 缓存，并在发送前检查当前会话是否已有消息。
  • [首页创建工作区成功但创建会话失败会留下半完成项目] → 保留已创建的 workspaceId，重试时仅重试会话创建，不重复创建新工作区。
  • [复用 AgentView 仍可能带入不适合 page-builder 的顶部或布局行为] → 通过最小参数化控制 header 等嵌入式行为，避免复制完整聊天实现。
  • [样式来源分散导致新 app 调整密度时出现不一致] → 复用现有视觉语言，但将 page-builder 的页面框架与紧凑布局样式收敛在自身目录内管理。
  • [左侧 iframe 缺少真实预览地址时用户感知不完整] → 明确第一阶段目标是页面与工作流骨架，预览容器先占位但保留真实嵌入结构。

Migration Plan

第一阶段不涉及后端数据模型迁移，也不修改现有工作区与会话存储格式。部署顺序以新增应用为主：

  1. 新增 apps/page-builder 及其构建配置。
  2. 在不破坏现有行为的前提下，为 apps/app 的相关对话组件增加 page-builder 嵌入所需的最小可配置能力。
  3. 接入现有 HTTP API，完成首页创建项目与 builder 初始化链路。
  4. 验证 page-builder 可以独立运行，并且不影响 apps/app 现有体验。

如需回滚，可直接移除 apps/page-builder 的入口与脚本；对 apps/app 的改动应保持为向后兼容的小改动，以便回滚成本最小化。

Open Questions

  • 当前阶段没有阻塞实现的产品问题。
  • 左侧 iframe 在后续阶段如何接入真实生成结果地址，属于后续预览能力设计，不阻塞本次首页与 builder 页面开发。
