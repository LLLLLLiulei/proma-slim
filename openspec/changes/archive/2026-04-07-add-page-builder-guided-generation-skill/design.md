## Context

`page-builder` 现在已经具备从首页输入一句需求、进入 Builder 双栏工作台、继续通过 Agent 生成和修改预览页的能力，但当前默认仍是自由对话。现有 page-builder 工作区模板虽然要求在关键信息不明确时使用 `AskUserQuestion`，并区分 `taste-skill`（实际 skill 名为 `design-taste-frontend`）与 `redesign-skill`（实际 skill 名为 `redesign-existing-projects`）的用途，但这些约束仍依赖模型自行判断，无法保证每次都先完成需求收敛、再稳定生成专题页。

本次变更面向无代码普通用户，首版目标是从一句模糊需求出发，生成一个单页专题页。系统已经有三类可复用能力：

- `AskUserQuestion`：支持单选、多选和自定义回答，适合口语化澄清
- `mentionedSkills`：支持在某一轮消息中显式强制装载指定 skill
- `workspace-files/index.html`：作为 page-builder 预览页的事实来源，可用于判断当前页面是否为空、是否进入迭代态

约束条件如下：

- 对用户提问时要保持普通用户可理解，但必要时可以保留少量专业网页术语，并在同一句中做简短解释；也不能要求答案足够精确
- 首版生成目标限定为单页专题页，不做多页站点编排
- 当前页面非空时，整页覆盖前必须再次确认
- 页面生成后，后续修改仍应沿用同一套主控逻辑，而不是切回完全自由对话

## Goals / Non-Goals

**Goals:**

- 为 `page-builder` 增加一个默认主控 skill，把专题页生成流程统一为“动态提问、必要澄清、汇总确认、整页生成、后续轻量迭代”
- 将用户确认、关键澄清和覆盖确认统一收敛到 `AskUserQuestion`
- 让主控 skill 在确认后显式驱动 `design-taste-frontend` 生成首版页面，并仅在必要时调用 `redesign-existing-projects` 提质
- 让 page-builder 的首页自动首发消息与后续普通输入都默认进入这套引导式流程

**Non-Goals:**

- 首版不处理多页专题站、整站路由和多页面导航
- 首版不把“重设计已有页面”作为主流程，只把它视为生成后的局部迭代或后续增强
- 首版不新增独立的可视化问卷 UI，继续复用现有 `AskUserQuestion` 横幅交互
- 首版不处理 CMS 绑定、内容同步或资源导出

## Decisions

### 1. 使用一个 page-builder 主控 skill 作为默认入口

新增一个 workspace-local 主控 skill，专门负责 `page-builder` 的专题页引导生成。它承担四类职责：

- 识别当前请求是在创建专题页、迭代当前页面，还是需要重新开始
- 以面向普通用户的方式组织动态问答和必要澄清
- 在信息足够后给出确认摘要并驱动页面生成
- 在页面已存在时，切换到轻量迭代模式而不是重新跑完整问答

该主控 skill 必须持续掌握普通用户侧的需求收集、关键澄清、最终确认和覆盖确认，不应把这些用户侧步骤再转交给 `brainstorming` 或其他元流程 skill。下游 skill 仅用于在确认后的生产阶段执行页面生成或提质。

之所以选择一个主控 skill，而不是把“需求收集”“确认”“页面生成”“重设计”拆成多个面向用户的 skill，是为了让 page-builder 对用户始终表现为一个连续助手，而不是一组需要用户理解和切换的技能集合。

在实现该主控 skill 时，推荐使用 `skill-creator` 来初始化 skill 目录骨架、`SKILL.md` 和 `agents/openai.yaml`，再将本设计定义的引导逻辑、`AskUserQuestion` 规则与下游设计 skill 编排补充进去。`skill-creator` 仅作为开发阶段的脚手架工具，不属于运行时依赖，也不应出现在面向用户的交互语义中。

**Alternatives considered**

- 仅增强 page-builder 工作区提示词：约束力不足，模型容易跳过提问与确认
- 拆成多个阶段性 skill：编排更复杂，且会把阶段切换暴露给用户

### 2. page-builder 发送链路默认强制注入主控 skill，而不是新增宿主状态机

宿主层在 page-builder 会话的两类发送路径中默认注入该主控 skill：

- 首页需求进入 Builder 后的首条自动发送
- Builder 右侧对话区的后续普通发送

注入方式继续使用现有 `mentionedSkills` 机制，而不是依赖可见文本中的 `/skill:` 指令。这样可以保证首轮和后续轮次都显式装载主控 skill。

为了避免为此再引入新的宿主状态机，本设计不要求主进程额外持久化“当前处于 briefing / confirm / iterate 哪个阶段”。主控 skill 自身根据以下信号推断当前模式：

- 当前会话历史
- `workspace-files/index.html` 是否已经存在非空页面
- 用户当前这轮输入是否表达“重新开始”“整体重做”或“局部修改”

这样可以把流程控制尽量放在 skill 内部，宿主只负责稳定注入。

**Alternatives considered**

- 在会话元数据里维护显式工作流阶段：可控但复杂，且需要处理刷新、恢复、异常中断等额外同步问题
- 只在首轮强制注入 skill，后续依赖模型记忆：稳定性不够，后续轮次容易漂移回自由对话

### 3. 结构化提问统一走 AskUserQuestion，遵循“一个关键问题 + 少量选项 + 自定义补充”

主控 skill 在收集需求、处理歧义、最终确认、整页覆盖确认时，统一使用 `AskUserQuestion`，并遵循以下规则：

- 一次只问一个当前最关键的问题
- 默认给 2 到 4 个通俗选项
- 始终允许“自定义回答”
- 仅在导航栏目、必备内容块等天然多值场景使用多选
- 用户说“你帮我决定”时，可在关键信息已足够的前提下停止追问并采用合理默认值

问题文案必须让普通用户容易理解，但不需要把所有术语都硬翻成特别口语化的说法。必要时可以保留术语并顺手解释。例如：

- 可以问“这个页面要不要做响应式，也就是手机和电脑都能比较自然地显示？”
- 可以问“Hero 区就是页面最上面的第一屏主视觉，你更想先突出标题还是先突出大图？”
- 不应问“请定义 Hero、CTA、信息架构、视觉层级、交互密度之间的优先级”

**Alternatives considered**

- 自由文本追问：对普通用户不稳定，且不利于收敛
- 自定义专用表单弹窗：交互成本高，也超出本次范围

### 4. 用“可稳定成稿阈值”决定何时停止提问并进入确认

主控 skill 不采用固定问卷，而是基于缺口追问。当以下信息已满足或可合理默认时，即可停止继续追问并进入确认：

- 页面是做什么的
- 主要给谁看
- 页面里最重要的内容块是什么
- 整体感觉偏什么方向
- 更偏手机还是电脑看
- 是否存在必须出现或必须避免的内容

在此阈值之下，skill 应优先继续补关键缺口；达到阈值后，应先生成一段面向用户的简报摘要，再用 `AskUserQuestion` 做最终确认，而不是直接开始写页面。

文案生成采用保守混合策略：

- 用户已提供的事实必须沿用
- 可合理补足的内容由模型生成可用草稿
- 强事实信息，如精确时间、资质、联系方式、价格、数据，不得编造
- 若页面结构仍需要承载这些强事实位置，则应使用“待确认”“待补充”等明确草稿占位，而不是伪装成最终真实信息

### 5. 页面生成采用“单页优先 + 非空覆盖确认 + 显式设计 skill 编排”

页面生成阶段分两种路径：

- **空白预览页**：确认完成后可直接生成单页专题页
- **非空预览页**：若当前用户意图是整页重做，主控 skill 必须先通过 `AskUserQuestion` 进行覆盖确认，确认后再写入

页面生成时，主控 skill 负责显式驱动下游设计能力：

1. 默认先调用 `design-taste-frontend` 生成接近最终效果的单页页面
2. 若结果仍明显模板化、层次不足或视觉不够成熟，再补一次 `redesign-existing-projects`

这样可以确保：

- `taste-skill` / `design-taste-frontend` 负责首稿生成的结构与视觉质量
- `redesign-skill` / `redesign-existing-projects` 只承担必要的提质职责，而不是每轮都介入

生成产物仍遵循 page-builder 现有规则：

- 主入口写入 `workspace-files/index.html`
- 其他资源按需写入 `workspace-files/assets/` 等相对路径
- 单页内导航默认使用锚点式区块跳转，而不是多页面跳转

**Alternatives considered**

- 始终只用主控 skill 直接生成，不显式调用下游设计 skill：难以稳定复用已有设计约束
- 每次都串行调用 `taste-skill` / `design-taste-frontend` 和 `redesign-skill` / `redesign-existing-projects`：成本更高，也会拉长主流程

### 6. 页面生成后继续由同一主控 skill 接管，但切换到轻量迭代模式

当 `workspace-files/index.html` 已经存在已生成页面后，主控 skill 对后续输入默认进入“优化当前页面”模式：

- 直接根据现有页面和用户新要求做局部修改
- 只有在需求存在关键歧义时，才再次使用 `AskUserQuestion`
- 不重新做完整需求收集

如果用户明确表达“重新做一版”“全部重来”“换成完全不同方向”，则重新回到覆盖确认与引导生成链路。

这个模式切换仍由主控 skill 根据预览文件和对话语义判断，不要求宿主保存额外阶段状态。

## Risks / Trade-offs

- [主控 skill 过于强势，限制熟练用户自由发挥] → 保留自定义回答，允许用户明确要求“你直接做决定”或“重新来一版”，并让主控 skill 在信息足够时尽快停止追问
- [过度依赖 AskUserQuestion 导致对话节奏变慢] → 严格执行“一次一个关键问题”，只在缺少会影响成稿质量的信息时才提问
- [始终强制注入主控 skill 可能把普通修改请求也带回问答流程] → 主控 skill 需优先根据现有预览页和用户意图进入轻量迭代模式，而不是默认重新收集需求
- [非空页面检测不准确，导致误覆盖] → 采用保守策略，只要 `workspace-files/index.html` 已存在非平凡内容，就在整页重做前再次确认
- [一次成稿质量波动较大] → 在正式生成前增加确认摘要，并通过显式驱动 `design-taste-frontend` 与按需驱动 `redesign-existing-projects` 降低结果波动
- [已有 page-builder 工作区缺少新 skill] → 提供默认 skill 同步机制，为既有工作区补齐缺失的主控 skill

## Migration Plan

1. 使用 `skill-creator` 初始化主控 skill 的目录骨架与基础元数据
2. 将主控 skill 加入 bundled default skills，并同步到后续新建的 page-builder 工作区
3. 为现有 page-builder 工作区补齐缺失的主控 skill，避免只有新项目才能使用该流程
4. 更新 page-builder 工作区模板提示词，使其与主控 skill 的职责边界一致
5. 在 page-builder 发送链路中默认注入该主控 skill
6. 若需要回滚，只需移除默认注入并保留现有自由对话链路，无需做内容数据迁移
