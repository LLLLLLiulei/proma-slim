## Context

当前 `page-builder` 已具备三块与本次需求直接相关的基础设施：
- Builder 可以通过预览桥接脚本在 iframe 内选中页面区块，并把当前区块表示为唯一 `selector`。
- 预览桥接脚本已经运行在真实预览 DOM 中，能够拦截点击、追踪布局变化，并把选区矩形回传给外层工作台。
- 预览内容来自工作区 `workspace-files/index.html`，且 Builder 已经能通过预览 `revision` 感知文件变化并自动刷新 iframe。

但目前仍缺一条“人工微调文案”的低成本链路。用户即使只想改标题、段落或按钮文案，也必须回到对话框继续描述修改，或者重新触发一次 Agent 生成。对高频、小幅、确定性的 copy 调整来说，这个回路太长。

这件事的关键难点不在于“如何让文字看起来可编辑”，而在于“如何只允许安全文本进入编辑态，并把改动稳定回写到 `workspace-files/index.html` 而不破坏 HTML 结构”。因此，第一阶段必须有意限制范围：只支持静态 HTML 中可稳定映射回源码的简单文本热点，不碰动态渲染文本、复杂富文本或数据源绑定内容。

## Goals / Non-Goals

**Goals:**
- 让用户在已选区块内直接点击简单文本热点进入内联编辑，而不再必须通过对话流改字。
- 在首版中支持区块内多个简单文本热点分别编辑，而不是只支持一个主文案。
- 采用失焦自动保存，将编辑结果写回 `workspace-files/index.html`，并让预览自动刷新到最新状态。
- 让链接文字和按钮文案在编辑优先级下拦截默认点击行为，保证“单击即编辑”成立。
- 保持现有选区心智：选区仍然是编辑作用域，内联编辑能力只在当前已选区块内启用。

**Non-Goals:**
- 不支持运行时 JavaScript 动态生成的文字内容编辑。
- 不支持复杂富文本嵌套、富文本工具栏、样式编辑或多段同时编辑。
- 不支持 CMS / 数据源绑定内容直接在预览中改字。
- 不支持每敲一个字都落盘；首版只做失焦自动保存。
- 不把整个区块设为 `contenteditable`，只支持文本热点级编辑。

## Decisions

### Decision: 以“已选区块 + 文本热点”两级模型实现编辑，而不是直接让整个区块可编辑

**Decision**
- 已选区块继续作为内联编辑的作用域。
- 在该作用域内只识别“简单文本热点”，例如 `h1`、`h2`、`h3`、`p`、`button`、`a`、纯文本 `span` 这类文本宿主元素。
- 只有文本热点本身进入编辑态，容器元素和复杂结构节点不进入编辑态。

**Rationale**
- 直接把整个区块设为 `contenteditable` 会把布局容器、图标、链接和按钮一起卷入浏览器原生编辑语义，极易破坏 DOM 结构。
- 用户已经明确要“区块内多个简单文本元素可分别编辑”，这天然要求“区块”与“编辑单位”分离。
- 两级模型能把当前选区继续作为心智锚点，同时让编辑动作足够细粒度。

**Alternatives considered**
- 整个区块 `contenteditable`：实现看似最省，但结构破坏风险最高。
- 只支持一个“主文案”热点：更简单，但会过度限制卡片、导航、按钮组合等常见区块。

### Decision: 采用单击进入编辑，并在编辑作用域内拦截链接/按钮默认点击行为

**Decision**
- 当区块已选中时，单击文本热点立即进入编辑态。
- 如果热点位于链接文字或按钮文案中，优先进入编辑，不触发原本跳转、提交或点击行为。
- 同一时刻只允许一个热点处于编辑态。

**Rationale**
- 用户已经明确选择“单击即编辑”，而不是双击或经过额外工具条。
- 若不拦截链接和按钮的默认点击行为，则“单击编辑”在最常见的 CTA 区块里无法成立。
- 限制单一活跃编辑态可以降低焦点管理、保存时机和回写冲突的复杂度。

**Alternatives considered**
- 双击进入编辑：更稳，但不符合已确认的交互方向。
- 通过工具条显式点击“编辑文字”再进入编辑：更保守，但损失了直接操作感。

### Decision: 保存时机采用失焦自动保存，而不是实时逐字落盘

**Decision**
- 用户离开当前热点编辑态时自动触发保存。
- 保存成功后让 `workspace-files/index.html` 更新，并依赖现有 `revision` 机制刷新预览。
- 保存失败时退出编辑态并提示错误，不保留“已保存”的假象。

**Rationale**
- 用户已经明确首版偏好失焦自动保存。
- 逐字落盘会导致频繁写文件、预览频繁刷新和编辑体验抖动。
- 失焦保存能把“浏览器原生编辑体验”和“代码侧稳定落盘”拉开一个合理边界。

**Alternatives considered**
- 每次输入后防抖保存：体验也可以，但仍会带来连续 revision 变化与 iframe 抖动问题。
- 每个按键立即保存：最实时，但首版风险过高。

### Decision: 主进程保存链路采用“显式保存 API + HTML 解析回写”，而不是在 iframe 内直接修改源文件

**Decision**
- renderer 不直接操作工作区文件。
- 新增一个专用保存接口，由主进程接收：
  - `workspaceId`
  - 区块 `selector`
  - 文本目标描述符 `textTargetDescriptor`
  - 新文本 `nextText`
- 主进程读取 `workspace-files/index.html`，通过 HTML 解析和确定性定位更新目标文本，再整体写回文件。

**Rationale**
- 预览 iframe 里的 DOM 只是运行时结果，不是源码本身；直接修改 iframe 内 DOM 无法自然持久化。
- 将写入集中在主进程可以统一处理路径安全、文件落盘和错误返回。
- HTML 解析回写比字符串搜索替换更稳，可以降低错误替换其他同名文本的概率。

**Alternatives considered**
- 只改 iframe DOM，不回写文件：视觉上可行，但刷新后会丢失。
- 在 `index.html` 中做纯字符串替换：实现快，但在重复文本、多相似节点场景下非常脆弱。

### Decision: 使用“文本目标描述符”而不是仅依赖块级 `selector` 定位回写目标

**Decision**
- 回写时不只传块级 `selector`，还要传递能在块内唯一定位文本热点的 `textTargetDescriptor`。
- 第一阶段的描述符应围绕“块内简单文本热点顺序 + 标签信息 + 子路径约束”构建，而不是只用最终可见文本做反查。
- bridge 端与 main 端需要共享同一套热点识别规则，保证预览中的第 N 个可编辑热点与源码解析结果中的第 N 个热点一致。

**Rationale**
- 一个区块内往往有多个可编辑文本，比如标题、描述、按钮文案；仅靠块级 `selector` 无法区分编辑目标。
- 仅靠旧文本内容做匹配，在“重复文案”或“多个按钮文字相同”时容易误命中。
- 显式描述符是首版最关键的数据模型，它决定了保存是否可预测。

**Alternatives considered**
- 用“旧文本内容”反查节点：实现简单，但重复文本时风险很大。
- 直接传整条 CSS 路径到文本节点：浏览器和解析器之间不一定完全稳定，且对微小结构变化过于敏感。

### Decision: 桥接脚本负责热点识别与编辑态编排，Builder 外层只负责状态和保存请求

**Decision**
- 预览桥接脚本增加两类责任：
  - 在当前已选区块内识别可编辑热点
  - 负责热点进入编辑态、退出编辑态和编辑中点击行为拦截
- Builder 外层负责：
  - 接收桥接发回的热点元信息
  - 调用保存 API
  - 展示保存失败反馈
  - 在预览刷新或选区失效时清理编辑上下文

**Rationale**
- 文本热点识别依赖真实 DOM 和用户点击目标，最适合留在 iframe 内部完成。
- 文件写回、错误提示和预览刷新是工作台级职责，应留在宿主层。
- 这样职责边界清楚：bridge 管“编辑交互”，Builder/main 管“持久化”。

**Alternatives considered**
- 把热点识别放到外层 renderer：缺少对 iframe 内真实 DOM 的直接掌控，复杂度更高。
- 把保存逻辑也放在 bridge：iframe 不应直接持有文件写权限，安全边界太差。

### Decision: 首版仅允许“能稳定回写”的热点进入编辑态

**Decision**
- 如果某个文本节点无法映射为稳定的 `textTargetDescriptor`，则该节点不进入编辑态。
- 对用户而言，这类文本表现为“不可编辑”，而不是先让用户编辑、保存时再失败。
- 首版的可编辑白名单和热点识别规则应明确保守。

**Rationale**
- 用户已经明确接受“第一阶段只支持静态 HTML 简单文本可编辑”。
- 先让用户进入编辑态再在保存时失败，会造成很强的落差感和不确定性。
- 首版应把“不能稳定保存”的复杂场景尽量前置过滤掉。

**Alternatives considered**
- 所有看起来像文字的节点都允许编辑，失败时再提示：表面更开放，但用户体验更差，且调试成本更高。

## Risks / Trade-offs

- **[热点定位在 bridge 与 main 端不一致]** → Mitigation: 共享统一的简单文本热点识别规则，并为典型 HTML 结构建立双端测试样例。
- **[HTML 解析回写改变源码格式]** → Mitigation: 首版接受最小必要的格式波动，但要避免结构性变化；必要时在设计中限制仅更新文本节点内容。
- **[保存导致预览刷新，可能打断当前编辑]** → Mitigation: 只在失焦后保存，并把“保存 -> revision 更新 -> 预览刷新”视为编辑结束后的自然阶段，而不是编辑中刷新。
- **[链接/按钮被拦截后与真实页面交互语义不同]** → Mitigation: 仅在当前已选区块且热点处于可编辑模式时拦截默认点击行为，平时仍保持原页面行为。
- **[复杂文本结构被误识别为简单热点]** → Mitigation: 首版使用严格白名单，宁可少支持，也不错误开放高风险节点。

## Migration Plan

1. 扩展预览桥接消息协议，增加可编辑文本热点与编辑态相关事件。
2. 在预览桥接脚本中加入“已选区块内简单文本热点识别”和 `contenteditable` 编辑态控制。
3. 在 Builder 外层增加当前编辑热点状态、保存请求和失败反馈处理。
4. 新增主进程保存 API 与 HTML writeback service，负责读取和更新 `workspace-files/index.html`。
5. 将保存完成后的文件变更纳入现有 preview revision 流程，复用 Builder 自动刷新机制。
6. 增加桥接、保存接口、HTML 回写和预览刷新联动测试。

**Rollback**
- 可以先移除桥接中的文本热点编辑能力，只保留现有区块选中和工具条逻辑。
- 即使保留保存 API，只要不从预览桥接触发内联编辑，也不会影响普通 Builder 工作流。
- 如果 HTML 回写策略不稳定，可暂时关闭入口并保留设计阶段抽象，不影响现有预览和对话编辑能力。

## Open Questions

- `textTargetDescriptor` 的最终形态是否需要在 specs 阶段显式标准化到共享类型中？
- 保存失败时的反馈更适合用轻量 toast，还是就近浮层提示？
- 首版是否需要支持 Enter 保留换行，还是限定为单行/自然段文本编辑？
