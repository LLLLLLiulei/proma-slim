## Context

`page-builder` 当前的左侧预览面板由 [`PreviewPane.tsx`](/Users/liu/Documents/work/learning/Proma/apps/page-builder/src/renderer/components/builder/PreviewPane.tsx) 统一负责，已经承载以下几类能力：

- 预览 iframe 的加载、刷新、全屏与新窗口打开
- 预览桥接消息接收，包括区块 hover / selected、内联文字保存等
- 已选区块工具条的显示、定位，以及图片替换 / CMS / 删除等操作入口

现状里，预览面板只提供单一桌面宽度视图，左上角仍是纯文本标题“实时预览”。这带来两个问题：

- 用户在 Builder 内无法直接检查移动端布局，响应式验证需要依赖浏览器开发者工具或单独开页面查看。
- 预览面板已经不再只是“被动展示”，而是承载区块选择、区块工具条和图片替换等高频交互，设备切换如果实现不当，会直接破坏已选区块工具条的锚定定位。

同时，现有代码已经提供了几个有利条件：

- `PreviewPane` 本身就是预览头部和 iframe 宿主的唯一拥有者，适合本地管理预览设备模式。
- 预览桥接脚本已经在选中元素位置变化时重发 `selected + rect`，包含窗口 resize 和 DOM 变化下的位置同步。
- `page-builder-app` 当前只在 spec 层禁止设备切换控件，并没有任何后端或协议层面对设备模式作出限制。

因此，这次设计的重点不是引入新的预览系统，而是在不改变预览入口和桥接协议边界的前提下，为现有 `PreviewPane` 增加一个可切换的真实视口容器。

## Goals / Non-Goals

**Goals:**

- 在 Builder 左侧预览面板中提供 `PC / Mobile` 设备切换入口，并替换现有“实时预览”标题占位。
- 默认使用 `PC` 模式；切换到 `Mobile` 时，以真实 `390px` 宽度驱动 iframe 重新布局。
- 保持现有“导出静态包”“刷新预览”“全屏预览”“新窗口打开预览”操作可用且交互语义不变。
- 保持已选区块工具条、区块选择高亮、图片替换和内联编辑等既有交互在切换视口后仍能正常工作。
- 将变更范围收敛在前端 `PreviewPane` 和对应测试内，不引入新的后端接口或第三方设备模拟库。

**Non-Goals:**

- 不增加 `Pad`、`Tablet` 等更多设备档位。
- 不引入手机外壳、设备边框、状态栏 mockup 或浏览器模拟器式工具栏。
- 不使用 `scale` / `transform` 对桌面预览做视觉缩放来伪装移动端。
- 不将设备模式持久化到 URL、工作区设置或 `localStorage`。
- 不修改工作区预览入口、预览状态接口、bridge 消息协议或 `BuilderPage` 的整体状态模型。

## Decisions

### 1. 设备模式状态收敛在 `PreviewPane` 本地，而不是提升到 `BuilderPage`

本次设备模式仅影响左侧预览面板的头部控件状态和 iframe 容器布局，不影响右侧对话区、工作区数据模型或后端协议。因此设备模式将作为 `PreviewPane` 的本地 UI 状态维护，例如 `desktop | mobile`，默认值为 `desktop`。

这样做的原因：

- `BuilderPage` 当前已经承担会话、选区、导出、CMS 弹框和区块操作等页面级协调逻辑，没有必要再承接一个只影响预览外壳的局部状态。
- 设备模式不参与消息发送，也不会影响工作区内容生成；保留在 `PreviewPane` 内能降低耦合。
- 后续如果用户刷新 Builder 页面，恢复默认 `PC` 模式是可以接受的，不需要为了短期状态恢复把它升级为全局状态。

备选方案：

- 将设备模式提升到 `BuilderPage` 并作为 prop 传入。可行，但会把纯局部展示状态扩散到页面级。
- 通过 URL 或 `localStorage` 持久化设备模式。当前收益很小，且会引入额外恢复逻辑与测试面。

### 2. 预览头部用图标切换器替代“实时预览”文字，不新增额外标题行

用户已经明确希望把“实时预览”文字删除，并将设备切换入口放在原位置。本次设计采用紧凑的双按钮切换器：

- `PC` 使用桌面图标
- `Mobile` 使用手机图标
- 仅显示图标，不显示文字标签
- 保留 `aria-label`、`title` 和选中态视觉反馈，保证可发现性和可访问性

推荐结构：

```text
┌──────────────────────────────────────────────────────┐
│ [PC] [Mobile]                 [导出] [刷新] [全屏] [新窗] │
├──────────────────────────────────────────────────────┤
│                                                      │
│                    preview viewport                  │
│                                                      │
└──────────────────────────────────────────────────────┘
```

这样做的原因：

- 预览头部本来就是一个紧凑工具栏，设备切换本质上也是项目级预览控制项，放在原标题位最符合当前布局。
- 图标切换器比再增加一行文字或下拉框更节省空间，不会挤压右侧已有四个控制按钮。
- 设备切换频率可能较高，双按钮比菜单层级更直接。

备选方案：

- 保留“实时预览”标题，并把切换器插到右侧按钮组中。会让头部过于拥挤，也和用户明确偏好不符。
- 使用下拉菜单或更多浏览器模拟控件。当前只需要 `PC / Mobile` 两态，不值得引入更复杂的控件形态。

### 3. `Mobile` 模式使用真实 `390px` 视口容器，不引入第三方库、设备外壳或缩放模拟

核心实现采用“真实 iframe 宽度变化”而不是“桌面页面整体缩小”：

- `desktop` 模式下，iframe 宿主容器占满当前预览可用宽度。
- `mobile` 模式下，在预览主体内部渲染一个居中的 viewport shell，目标宽度为 `390px`，高度继续占满可用区域。
- iframe 始终 `width: 100%; height: 100%`，由 viewport shell 的真实宽度驱动页面响应式重排。

这意味着本次不会引入任何第三方设备模拟组件，也不会加入手机边框、阴影壳体或地址栏模拟。

这样做的原因：

- 当前页面区块选择高亮和区块工具条都依赖 iframe 内真实布局结果。改变真实宽度是最自然、最稳定的响应式验证方式。
- 若使用 `scale` 或 mockup 库，父层工具条坐标会受到额外缩放和偏移影响，复杂度明显上升。
- 现有 `PreviewPane` 结构已经足以承载一个真实视口容器，不需要额外依赖。

备选方案：

- 使用 `react-device-mockup` / `react-device-frameset` 一类第三方库。它们更适合做视觉外壳，不适合当前“桥接选区 + 外层工具条”的组合场景。
- 对整张 iframe 应用 `transform: scale(...)`。视觉上能模拟手机，但会让选中区块定位、点击区域和父层工具条锚定一起变复杂。

补充约束：

- 正常 Builder 布局下应优先保持 `390px` 宽度。
- 若预览容器本身比 `390px` 更窄，则允许 viewport shell 向容器宽度收敛，以避免引入横向滚动或裁切。

### 4. 已选区块工具条的锚定基准改为“实际视口容器”，而不是整个预览外框

当前 `PreviewPane` 中的区块工具条定位基于整个 `frameRef` 的尺寸计算。桌面全宽时这没有问题，但移动端模式会在容器中间形成左右留白，若继续以整个外框为坐标系，工具条会相对 iframe 内容发生水平偏移。

因此本次设计将预览主体拆成两层：

- 外层 `frameRef`：继续负责面板边框、背景和全屏宿主
- 内层 `viewportShellRef`：实际承载 iframe 与 overlay 的相对定位容器

推荐结构：

```text
frameRef (full preview body)
└─ viewportShellRef (desktop: full width / mobile: 390px centered)
   ├─ iframe
   └─ overlay host
      └─ PageBuilderBlockActionBar
```

变化点：

- `PageBuilderBlockActionBar` 继续由父层 React 渲染，不注入 iframe 内部。
- `resolveBlockActionBarStyle(...)` 的尺寸基准改为 `viewportShellRef`。
- overlay host 跟随 `viewportShellRef` 一起居中，从而让 bridge 回传的 `rect` 仍然可以直接作为视口内坐标使用，不需要再额外叠加左右偏移。

这样做的原因：

- 预览桥接脚本已经用 `getBoundingClientRect()` 回传 iframe 视口坐标；只要 overlay 和 iframe 共享同一个相对定位容器，就不需要新增协议或额外偏移换算。
- `PageBuilderBlockActionBar` 作为 Builder UI 的一部分，继续保留在 iframe 外层渲染最符合现有架构。

备选方案：

- 保持 overlay 覆盖整个外框，再额外叠加 `viewportShell` 的 left offset。可以实现，但坐标换算和后续维护都更脆弱。
- 把工具条直接渲染到 iframe 内。会让 Builder UI 逻辑进入用户页面 DOM，不符合当前边界。

### 5. 切换设备模式时保留现有预览操作语义，不引入新的后端协议或打开方式

本次设备切换只改变 Builder 内嵌预览的容器宽度，不改变预览页面本身的 URL 协议与行为：

- 手动刷新仍然只重载当前 iframe
- 全屏仍然针对整个预览面板容器生效，并保留当前 `PC / Mobile` 模式
- “新窗口打开预览”仍打开真实 `previewUrl`，不会额外附带“移动端模式”参数
- 导出静态包逻辑完全不受影响

这样做的原因：

- 设备切换是 Builder 内的检查视角，而不是工作区页面产物本身的状态。
- 若把设备模式编码进 URL 或后端接口，会误导后续功能把它当成页面发布语义的一部分。

备选方案：

- 为 `previewUrl` 增加 viewport 查询参数。当前没有必要，而且服务端也不需要知道 Builder 选择了哪种本地预览方式。

### 6. 复用现有 bridge 的位置更新能力，不因设备模式切换而额外清空选区

预览桥接脚本已经在以下场景同步选中元素的 `rect`：

- 首次选中时
- `window.resize`
- DOM 变更导致布局变化时

因此，设备模式切换后 iframe 尺寸变化会自然触发 iframe 内部的 resize，bridge 会继续推送新的 `selected + rect`，从而驱动工具条重新锚定。基于这一能力，本次不主动在设备切换时清空当前选区。

这样做的原因：

- 用户切换 `PC / Mobile` 的目的就是在同一上下文中继续检查当前页面和当前区块；主动清空选区会打断流程。
- 现有桥接已经具备布局变化后的重新同步能力，没必要再为此引入新的状态机。

备选方案：

- 每次切设备都强制 `reset` 当前选区。实现更保守，但会明显降低工具条和区块编辑链路的连续性。

### 7. 测试重点放在 `PreviewPane` 组件行为回归，而不是新增端到端预览协议测试

本次变更是纯前端容器级能力，不改后端预览接口，也不改 bridge 消息结构，因此测试重点应集中在：

- 头部不再渲染“实时预览”文字
- 头部新增 `PC / Mobile` 两态图标切换按钮
- 默认 `PC` 模式下仍保持现有预览与按钮结构
- 切换到 `Mobile` 后，viewport shell 应进入 `390px` 目标宽度的居中布局
- 已选区块工具条在两种模式下都继续基于实际视口容器渲染
- 导出 / 刷新 / 全屏 / 新窗口等现有按钮行为不回归

这样做的原因：

- 主要风险集中在 UI 结构调整和局部定位坐标，不在于数据流或外部接口。
- 将测试面控制在 `PreviewPane.test.tsx` 内，可以用最小成本覆盖最大风险点。

## Risks / Trade-offs

- [Risk] 当 Builder 预览可用宽度本身小于 `390px` 时，移动端模式无法保持严格的 `390px` 真实宽度
  → Mitigation: 以 `390px` 作为目标宽度，在宿主更窄时收敛到可用宽度，优先保证不裁切、不出现额外横向滚动。

- [Risk] 预览主体新增居中 viewport shell 后，区块工具条可能因为错误的坐标基准发生偏移
  → Mitigation: 让 overlay host 与 iframe 同属于 `viewportShellRef`，避免在外层做额外偏移换算。

- [Risk] 切换设备模式时，若 bridge 位置更新晚于父层渲染，工具条可能短暂显示旧位置
  → Mitigation: 依赖现有 bridge 的 resize/mutation 同步能力，必要时在父层保留现有选中态但等待下一帧位置更新，不引入额外持久旧坐标逻辑。

- [Risk] 图标化切换器移除文字标题后，首次使用者可能无法立即识别按钮含义
  → Mitigation: 保留清晰的 `title` 和 `aria-label`，并使用明确的选中态样式区分当前模式。

- [Risk] 未来若要扩展更多设备模式，当前两态切换器可能需要重构
  → Mitigation: 首版明确只支持 `PC / Mobile`，后续如需加入 `Pad` 再单独升级为更通用的设备模式控件。

## Migration Plan

1. 在 `PreviewPane` 中新增本地设备模式状态，并将头部左侧从文字标题改为 `PC / Mobile` 图标切换器。
2. 为预览主体引入 `viewportShellRef`，在 `desktop` 和 `mobile` 模式下切换不同的宽度与居中布局。
3. 将 iframe 和区块工具条 overlay 一起挂到 `viewportShellRef` 下，并把工具条定位基准从外层 `frameRef` 调整为实际视口容器。
4. 更新 `PreviewPane` 组件测试，覆盖设备切换、新布局和现有按钮/工具条行为不回归。
5. 在后续 spec 阶段同步更新 `page-builder-app` 对预览控制项的描述，并新增 `page-builder-device-preview` capability。

回滚策略：

- 若设备切换引起不可接受的定位问题，可直接移除 `PreviewPane` 中的设备切换器和 `viewportShell` 结构，恢复单一全宽 iframe 容器；由于不涉及后端接口和持久化数据，回滚成本较低。

## Open Questions

- 后续若要支持 `Pad`、设备外壳或模式持久化，应作为独立变更重新评估，而不是在本次实现中预留复杂状态模型。
