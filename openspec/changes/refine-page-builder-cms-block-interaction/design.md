## Context

`page-builder` 目前已经具备与本次改动直接相关的几项基础能力：

- 左侧预览、右侧对话的 Builder 工作台
- 预览区块的 hover / selected 高亮与下一条消息一次性选区上下文注入
- Builder 内部 CMS 选择器模态框
- `RequestCmsSelection`、`AskUserQuestion`、CMS 隐藏上下文装饰、绑定持久化与资源导入链路

当前问题不在于 CMS 接入能力缺失，而在于手动 CMS 入口的位置和语义不自然。现在手动 `从 CMS 选择` 放在聊天输入区左下角，本质上是复用了现有消息发送和隐藏上下文机制，但对普通用户而言，它像是一个“聊天工具”，而不是“针对当前区块的页面操作”。这带来几个实际问题：

- 用户不知道是应该先选区块，再点 `从 CMS 选择`
- 用户可以直接选 CMS，但界面没有清楚表达“这份数据将作用于哪里”
- 一个强依赖当前目标区块的动作，被放在了全局聊天输入区

用户已经明确了新的产品方向：

- 手动 `从 CMS 选择` 的主入口要放在预览区已选区块下方
- 第一版区块工具条只放这一个按钮
- 用户确认 CMS 数据后，默认自动开始修改，不再要求额外补一句描述
- 只有在当前区块与所选 CMS 数据无法很好匹配时，才通过 `AskUserQuestion` 做最小必要确认
- 聊天区要出现一条用户可见的系统代发消息
- Agent 在对话中主动触发 CMS 选择器的链路继续保留，但不再是主入口

因此，这次设计的核心不是重做 CMS 接入，而是重构“手动 CMS 入口”和“确认后的执行路径”，同时尽量复用现有组件和运行时链路。

## Goals / Non-Goals

**Goals:**

- 让手动 CMS 选择明确成为“作用于当前选中区块”的操作，而不是脱离预览区的聊天工具。
- 将手动 `从 CMS 选择` 入口从聊天输入区迁移到预览区已选区块下方的浮动工具条。
- 用户确认 CMS 数据后默认自动开始修改，并在聊天区生成一条可见的系统代发消息。
- 仅在存在明显不匹配或目标不明确时，才通过 `AskUserQuestion` 追问。
- 保持 Agent 自然语言触发 CMS 选择器的链路可用，并与当前选中区块状态协同。
- 尽量复用现有 `PageBuilderCmsPickerModal`、隐藏上下文装饰、绑定持久化和资源导入实现。

**Non-Goals:**

- 不重写现有 CMS 运行时、`cms_*` 数据工具、资源导入与绑定持久化。
- 不在本次引入完整的区块编辑工具条，仅增加 `从 CMS 选择` 一个动作。
- 不把所有自然语言驱动的 Builder 编辑都改成自动执行；本次只覆盖“区块下方的手动 CMS 选择”这一主路径。
- 不实现复杂的块类型智能识别引擎；第一版只做保守的少量冲突判断。
- 不改变预览区块“仅维护一个当前目标”的基础选区模型。

## Decisions

### 1. 手动 CMS 主入口迁移到已选区块下方，而不是继续保留在聊天输入区

这次改动会把 Builder 页聊天输入区中的手动 `从 CMS 选择` 入口移除，并在预览区当前已选中区块下方新增一个浮动工具条。第一版工具条只包含一个动作：

- `从 CMS 选择`

这样做的原因：

- 它把操作位置和目标对象直接绑定，用户看到按钮时就知道是在操作当前区块
- 避免普通用户去理解“下一条消息生效”“隐藏上下文”这类内部机制
- 区块级动作回归预览区，聊天输入区继续承担纯对话职责

备选方案：

- 保留聊天输入区入口不动，仅靠文案解释“请先选区块”。改动小，但不能真正解决心智混乱。
- 区块下方和聊天输入区都保留手动入口。会继续制造两个主入口，普通用户更难判断该用哪个。

### 2. 区块工具条只做入口层，不承载 CMS 数据逻辑

新增一个轻量的区块工具条组件，用于渲染锚定在当前选中区块下方的浮动操作条。它只负责：

- 展示按钮
- 响应点击
- 反映当前是否处于打开选择器或自动应用中的忙碌态

它不负责：

- 加载 CMS 数据
- 决定是否自动应用
- 触发 Agent 执行

这部分逻辑仍由 `BuilderPage` 编排，并通过独立的自动应用 helper / hook 协调。

这样做的原因：

- 防止把 CMS 选择、消息发送、追问逻辑重新塞回一个纯 UI 组件
- 保持区块工具条可扩展，后续如果再增加“删除区块”“在下方新增”等动作，不会影响 CMS 链路内部实现

备选方案：

- 直接在 `PreviewPane` 内部硬编码渲染和执行逻辑。实现快，但状态很快会和选区、iframe 通信、CMS 选择器互相缠绕。

### 3. CMS 选择器继续复用现有模态框，但新增 block-bound 手动模式

`PageBuilderCmsPickerModal` 继续作为共享组件存在，不重写选择器内部实现。手动区块工具条打开它时，进入一种新的语义模式：

- 当前正在“为已选区块选择 CMS 数据”
- 确认后会直接继续进入修改

而 Agent 主动触发 `RequestCmsSelection` 时，依然沿用原有 Agent-requested 语义。

这样做的原因：

- 现有选择器已经具备栏目树、内容搜索、筛选、卡片预览、确认/取消和结构化结果返回能力
- 当前问题在入口与后续动作，不在 CMS 选择器内部能力不足
- 共用同一套组件和结果协议，可以避免 manual / agent 两条链路分叉

备选方案：

- 为区块工具条单独再做一个“简化版 CMS 选择器”。会造成两套选择器状态和协议维护。

### 4. 手动区块链路在确认 CMS 后默认自动执行，而不是继续等待用户输入

对于“用户先选中区块，再从区块工具条进入 CMS 选择”这条主路径，用户完成 CMS 选择后默认直接开始本次修改。前端会自动触发一次面向 Agent 的请求，而不是要求用户再补一句自然语言。

内部仍然复用现有隐藏上下文装饰：

- `<page_builder_selection>`
- `<page_builder_cms_selection>`

但这次不再由用户手动点击发送触发，而是由自动应用编排层触发。

这样做的原因：

- 用户已经通过两个明确动作表达了意图：“我要改这块”“我要用这份 CMS 数据”
- 继续要求用户手动补一句描述，会把体验重新拉回“工具链路已打通，但产品流程不顺”的状态

备选方案：

- 选完后让用户继续手动输入。最贴近当前实现，但无法解决用户困惑。
- 选完后静默执行，不在聊天中留下任何记录。技术上可行，但用户会不知道系统是否真的开始工作。

### 5. 自动执行必须生成一条用户可见的系统代发消息

当系统自动开始修改时，聊天区必须插入一条可见的系统消息，用自然语言表达当前动作，例如：

- 已将当前区块与所选 CMS 数据关联，正在生成修改。

这条可见消息不暴露 selector、CMS 原始字段或结构化协议细节；真正的 Agent 输入仍然继续依赖隐藏上下文装饰链路。

这样做的原因：

- 用户需要知道系统不是“悄悄执行了什么”，而是清楚地开始了当前区块的 CMS 应用流程
- 保留对话历史的可读性，同时不污染用户可见文本

备选方案：

- 完全静默执行。透明度不足。
- 在聊天里展示原始结构化 payload。会把技术细节暴露给普通用户。

### 6. 追问改为例外路径，只在明显不匹配时调用 `AskUserQuestion`

这次不会把 `AskUserQuestion` 放进默认流程，而是作为例外分支。第一版只覆盖少数高价值冲突场景，例如：

- 当前区块显著像单图 / 单卡片 / 单媒体，而用户选择了 `channel-children` 或 `content-list`
- 当前区块显著像导航 / 菜单，而用户选择了 `content-item`
- 用户通过自然语言触发 CMS 选择器，但当前没有选中区块，系统无法判断是替换已有区域还是新增一个区块

一旦命中这些情况，系统通过 `AskUserQuestion` 做一次短确认，再继续执行。

这样做的原因：

- 让主流程尽量流畅，不把所有用户都拉进追问
- 对普通用户而言，少量结构化确认比要求自由输入更稳定

备选方案：

- 每次都追问。稳，但太慢。
- 永不追问。快，但容易在错误目标或错误结构上直接生成。

### 7. Agent 自然语言触发 CMS 选择器继续保留，但降级为补充入口

对话里主动表达“把这块改成 CMS 内容”“这里下方加一个轮播图，图片从 CMS 选”等意图的场景仍然保留。系统处理方式变为：

- 如果当前已经有选中区块，则默认作用于当前区块
- 如果当前没有选中区块，则先判断是否需要用 `AskUserQuestion` 确认是在修改已有区块还是新增区块，再决定如何继续

这样做的原因：

- 用户已经明确要求保留自然语言触发 CMS 选择器的能力
- 但这条链路不应该再作为手动 CMS 的主入口，否则会继续和区块工具条主路径竞争

备选方案：

- 完全移除自然语言触发。会损失现有对话驱动场景。

### 8. 这次实现以最小侵入方式复用现有消息、绑定和资源链路

本次 change 不改动 CMS 接入基础层，只调整触发方式和上层编排。要继续复用：

- `PageBuilderCmsPickerModal`
- `RequestCmsSelection`
- `cms_*` 数据工具
- 现有隐藏上下文消息装饰
- CMS 绑定持久化
- 资源导入逻辑

主要新增 / 调整的是：

- 区块工具条组件
- `BuilderPage` 的状态编排
- 自动应用 helper / hook
- 相关测试

这样做的原因：

- 当前 CMS 集成主链路已经打通，没必要为了入口交互而重写底层能力
- 这样可以把风险集中在 Builder 页交互层，而不是扩散到整个运行时

## Risks / Trade-offs

- [Risk] 预览选区、CMS 选择器、自动执行、`AskUserQuestion` 四段状态容易缠绕
  → Mitigation: 明确维持 `idle` / `block-selected` / `cms-picking` / `auto-applying` / `needs-clarification` 这类有限状态，并把自动应用逻辑从纯 UI 组件中拆出来

- [Risk] 区块工具条需要跟随选中区块定位，预览区滚动、iframe 变化或预览刷新时可能导致位置错乱
  → Mitigation: 工具条依附于现有选区桥接与选区状态；预览刷新后沿用“选区失效”规则，工具条也同步消失

- [Risk] 不匹配判断过于激进会让用户频繁被追问，体验变慢
  → Mitigation: 第一版只覆盖明显冲突的少量情况，不做复杂推断

- [Risk] 自动生成的系统消息如果写得过于技术化，仍然会让普通用户困惑
  → Mitigation: 将可见消息限定为产品文案，结构化数据仍只保留在隐藏上下文中

- [Risk] 自然语言触发路径和区块工具条路径若状态不一致，会让结果难以预测
  → Mitigation: 将“当前已选区块优先”作为统一规则，两条路径最终汇合到同一套 CMS 选择结果和自动应用编排上

## Migration Plan

1. 先补充和更新 OpenSpec delta specs，明确手动 CMS 入口迁移、自动执行与最小追问的 requirement 变化。
2. 在 `apps/page-builder` 中为选中区块新增浮动工具条组件，并从聊天输入区移除手动 `从 CMS 选择` 入口。
3. 复用现有 CMS 选择器模态框，为其补充 block-bound 手动模式的 framing。
4. 新增自动应用编排层：生成系统代发消息、组合隐藏上下文、触发 Agent 执行、按需进入 `AskUserQuestion`。
5. 让自然语言触发 CMS 选择器的链路与当前选中区块状态协同，统一到同一套编排逻辑。
6. 补充前端与运行时测试，覆盖区块工具条、自动执行、取消回退、冲突追问与原有 CMS 能力不回退。

回滚策略：

- 如果区块工具条或自动应用带来明显交互回归，可以先回退到“保留当前区块工具条，但确认后不自动执行”，仍不需要恢复聊天输入区中的旧入口
- 如果自动应用编排本身不稳定，可暂时保持区块工具条入口，但回退到“选择后等待用户确认发送”的模式，以保护已有 CMS 选择器与数据链路

## Open Questions

- 第一版“不匹配判断”应当依赖哪些稳定信号来做保守判断：区块标签名、文本密度、是否含图片，还是仅依赖 Agent 提供的 `presentationHint`？
- 系统代发消息的最终用户文案是否需要区分 `channel-children`、`content-item`、`content-list` 三类主要数据源，以便更准确表达当前动作？
- 对于“无当前选中区块，但用户在聊天中要求用 CMS 新增一个区块”的场景，第一版是先用 `AskUserQuestion` 确认插入位置，还是直接交给 Agent 自由决定？
