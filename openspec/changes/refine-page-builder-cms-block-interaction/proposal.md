## Why

当前 `page-builder` 已经具备区块选中和 CMS 选择能力，但手动 `从 CMS 选择` 入口放在聊天输入区，普通用户很难理解它与当前选中区块之间的关系，也不清楚“先选区块还是先选 CMS”。这导致 block-scoped 的操作被呈现成了 chat-scoped 的工具，交互心智不自然，已经影响到 CMS 数据接入场景的可用性。

## What Changes

- 将手动 `从 CMS 选择` 的主入口从聊天输入区迁移到预览区已选区块下方的浮动工具条中，明确它是“作用于当前区块”的操作。
- 第一版区块工具条只提供一个动作：`从 CMS 选择`，不在这次变更中扩展为完整的区块编辑工具条。
- 用户为当前区块确认 CMS 数据后，系统默认自动开始修改，而不是要求用户继续补一句自然语言描述。
- 自动开始修改时，在聊天区插入一条用户可理解的系统代发消息，用于说明“已为当前区块应用所选 CMS 数据并开始生成”。
- 仅在系统判断“当前区块”和“所选 CMS 数据源”无法安全匹配时，才通过 `AskUserQuestion` 做最小必要确认，而不是把追问作为默认路径。
- 保留 Agent 在对话中主动触发 CMS 选择器的链路，但将其降级为补充入口；当存在当前选中区块时，该链路默认作用于当前区块。
- 继续复用现有的 CMS 选择器模态框、隐藏上下文注入、绑定持久化与资源导入链路，不重写 CMS 接入基础能力。

## Capabilities

### New Capabilities
- `page-builder-cms-block-actions`: 定义 Builder 预览区已选区块下方的 CMS 工具条、CMS 确认后的自动应用、最小追问分支，以及系统代发消息的行为边界。

### Modified Capabilities
- `page-builder-preview-block-selection`: 扩展已选区块的交互边界，使选中的区块可以承载与当前目标强绑定的浮动操作条，同时保持单目标选区、选区失效和下一条消息上下文的生命周期约束。

## Impact

- 影响 `apps/page-builder` 中 Builder 页、预览区选区交互、区块工具条渲染与 CMS 选择后的自动执行编排。
- 影响现有 `PageBuilderCmsPickerModal` 的使用语义与文案 framing，但不改变其作为共享选择器组件的定位。
- 影响 page-builder 运行时中“手动 CMS 选择”的入口位置与消息触发方式，需要与现有 `RequestCmsSelection`、`AskUserQuestion`、隐藏上下文装饰和绑定持久化链路协同。
- 需要新增或调整前端测试，以覆盖区块工具条、自动应用、系统代发消息以及冲突场景下的最小确认流程。
